# 外部片单「站内播放」实现说明

> 对应需求：外部片单条目必须在站内直接播放，不得跳转到原站观看。
> 实现范围：Web 端（`web/`）+ EdgeOne 云函数（`makers/cloud-functions/api/v1/ext/`）。

## 一、为什么必须有服务端参与

需求听起来是前端的事，但有一道浏览器层面的墙绕不过去：

**iframe 被 `X-Frame-Options` / CSP `frame-ancestors` 拦掉时，浏览器不给 JS 任何信号。**
不报错、不触发 `error` 事件，`load` 事件照常触发（加载的是内部错误页）。也就是说前端
**无法区分「加载成功」和「被安全策略静默拦截」**，更拿不到拒绝原因。

同理，`<video>` 拿不到 HTTP 状态码——源站返 403（防盗链）还是 404（已下架），
前端无从判断，只能笼统显示"播放失败"。

所以把这两件事搬到服务端，由服务端读响应头、抽取播放流，把**结论**下发给前端：

```
浏览器 → /api/v1/ext/play → 云函数拉源站页面
                              ├─ 读 X-Frame-Options / CSP frame-ancestors → 能否被 iframe 嵌入
                              ├─ 从页面抽 m3u8/mp4                        → 能否走直链播放
                              └─ 返回 { mode, sources[], embed_url, reason }
浏览器 ←─ 三选一的明确结论 ───────────────┘
```

## 二、三档降级

| 档 | 触发条件 | 播放方式 | 用户体验 |
|---|---|---|---|
| `direct` | 拿到可直接播放的地址 | 本站 `<video>` + hls.js | 最好，等同自有内容 |
| `embed` | 拿不到流，但源站未禁止嵌入 | `sandbox` iframe 加载源站播放页 | 页面中播放，含源站自身 UI |
| `blocked` | 以上都不成立 | 统一失败面板 + 原因说明 | 明确告知，附重试与降级确认 |

**默认行为永远是站内播放。**前往原站需要用户完成两步：
① 在失败面板点「仍要前往原站」→ ② 在二次确认弹窗点「我已了解，前往原站」。
组件本身不持有跳转能力——`onOpenOriginal` 是外部传入的回调。

## 三、接入一个新的播放源

所有外部源集中登记在 `makers/cloud-functions/_lib/ext_providers.js`，**这是唯一的可信边界**，
新增源站无需改动任何前端代码。

适配器完整形态（以红果为例，已实现全部四项能力）：

```js
const example = {
  key: 'example',
  label: '示例短剧',
  hosts: ['example.com', 'www.example.com'],
  /** 视频 CDN 后缀白名单，proxy 放行用（只匹配子域，不匹配根域） */
  cdnSuffixes: ['.example-cdn.com'],
  /** 已知带 Referer 防盗链 → 直接优先下发代理地址 */
  antiLeech: false,
  /** 播放器页地址；返回 null 表示没有独立播放器页 */
  buildPlayerUrl: (item, url, ep) => `https://example.com/player/${id}/${ep}`,
  /** 兜底嵌入页 */
  buildEmbedUrl: (item, url) => url.toString(),
  /** 从播放器页 HTML 里抠真实流地址；返回 [] 则由调用方降级到 embed */
  extractStreams: (html) => [{ url, container: 'mp4', quality: 'auto' }],
};
export const PROVIDERS = [hongguoduanju, example];
```

登记后自动获得：SSRF 白名单放行、防盗链代理放行、可嵌入性预检。

### 三种提升播放质量的方式（按优先级）

1. **让服务端从播放器页抠出真实流（当前红果采用，已落地）**
   实现 `buildPlayerUrl` + `extractStreams`，直接升到 `direct`——用自己的播放器播，
   不带源站页面 UI。红果正是靠这条从 `embed` 升级的，详见第四节。
2. **采集期写入 `play_url`**
   在 `web/public/external/<cat>.json` 的条目上加 `play_url` 字段，`ext/play` 会直接采用，
   连源站都不用请求，响应最快。要求必须是 `https://` 绝对地址（冒烟脚本会校验）。
3. **什么都不做**
   只要源站没设 `X-Frame-Options: DENY/SAMEORIGIN` 或 `frame-ancestors 'none'`，
   就自动落到 `embed` 档。

接入完成后跑：`node scripts/sync_external_data.mjs`（把同步云函数可读目录）。

## 四、防盗链处理

很多 CDN 按 Referer 校验。直接把外部地址交给 `<video>` 会带上本站 Referer，容易被拒。

`GET /api/v1/ext/proxy?src=<url>` 由云函数代为取流，请求不带本站 Referer：

- **m3u8**：逐行重写内部 URI（分片、`EXT-X-KEY`、`EXT-X-MAP` 的 `URI="..."`），
  否则分片仍直连源站，防盗链照样生效。
- **mp4/webm**：原样转发，支持 `Range`（206 必须透传，否则拖动进度条会错乱）。
- 体积上限 `MAX_PROXY_BYTES`，超时 15s。

### 红果实测数据（2026-10-05）

同一签名地址，三种 Referer 下的结果：

| 请求方式 | 结果 |
|---|---|
| 不带 Referer | ✅ `206 video/mp4` |
| 带源站 Referer | ✅ `206` |
| 带**本站** Referer | ❌ **403** |

结论：浏览器直连**必然**带本站 Referer → 必然 403，所以红果条目必须走代理。
适配器里因此标了 `antiLeech: true`，服务端下发 `proxied_first: true`，
前端把这个源的代理地址排在最前，**省掉一次注定失败的直连尝试**。

### 尝试顺序

- 默认：每个源按 **直链 → 代理** 自动尝试；
- `proxied_first: true` 时：**代理 → 直链**（已知防盗链的源）。

全程无需用户干预，失败才进入降级 UI。

> 类型判定注意：字节系 VOD 的地址**不带文件扩展名**
> （形如 `/.../video/tos/.../?a=8662&...&mime_type=video_mp4`），
> 只认 `.mp4` 后缀会误杀。`ext/proxy` 因此同时识别 `mime_type=video_*` 查询参数，
> 并在拿到上游响应后按 `Content-Type` 二次校验非媒体即拒绝。

## 五、错误码与文案映射

服务端 `reason` → 前端 `FailureCode` → 用户可见文案（`ExternalPlayer.tsx` 的 `FAILURE_TEXT`）：

| 服务端 reason | 前端 code | 用户看到 |
|---|---|---|
| `stream_expired` | `expired` | 片源已失效（403/404），不建议重试 |
| `frame_blocked` | `frame_blocked` | 源站禁止嵌入，第三方无法绕过 |
| `host_not_allowed` / `no_adapter` | `unknown` | 无法在该来源播放 |
| `unreachable` | `network` | 连不上，可重试 |
| —（`<video>` SRC_NOT_SUPPORTED，未走代理） | `cors` | 跨域限制，已自动改走本站转发 |
| —（同上，已试过代理） | `hotlink` | 源站防盗链拦截 |
| —（iframe 15s 未 load） | `frame_timeout` | 嵌入加载超时，可重试 |
| —（MEDIA_ERR_DECODE） | `decode` | 格式不受支持，建议换浏览器 |

每个错误都给出「原因 + 怎么办 + 是否值得重试」，不做笼统的"播放失败"。

## 六、安全红线

1. **iframe sandbox 绝不含 `allow-top-navigation`**。一旦放开，第三方页面能劫持顶层导航，
   把用户静默带到原站——"站内播放"就名存实亡。冒烟脚本有断言守着这条。
2. **出站必须过白名单**。`authorize()` 在 `ext/play` 与 `ext/proxy` 里都是第一道关卡：
   只放行 `PROVIDERS` 登记的主机、只接受 https、拒绝 IP 直连与内网地址。
3. **禁止 `window.open` 直跳**。沿用既有的 `<a target="_blank" rel="noopener external">` 方式，
   并且刻意不加 `noreferrer`（反向链接凭证要留给源站，跨源默认只发 origin）。
4. **云函数出网超时 8s**（`maxDuration` 是 30s），避免慢源拖垮实例。

## 八、红果短剧的实测结论（2026-10-05）

片单 2010 条**全部**来自 `hongguoduanju.com`，所以搞清楚它一家就等于覆盖全站。

| 探测项 | 结果 |
|---|---|
| `/detail?series_id=<id>` | 200，混淆 SSR 包，无明文流地址 |
| `X-Frame-Options` / CSP `frame-ancestors` | 均无；HTML 里也无 frame-buster → 可嵌入 |
| `/player/<sid>/<ep>` | **200**，`robots.txt` 的 Disallow 暴露了这条路由 |
| 播放器页里的真实地址 | SSR 数据字段 **`main_url`**，指向 `v*-hgweb.qznovelvod.com` 的签名 mp4 |
| 该地址的防盗链 | 不带 Referer ✅ / 源站 Referer ✅ / **本站 Referer ❌ 403** |
| 签名有效期 | 实测 3 分钟后仍 206；缓存取 5 分钟，并支持 `fresh=1` 强制跳过缓存 |

**因此红果已从 `embed` 升级为 `direct`**：用自己的播放器播真实 mp4，
不再套源站页面 UI。关键在 `main_url` 的提取——源站把 `/` 转义成了 `\u002F`，
必须先还原再正则匹配，否则什么都抠不到。

## 九、已知边界

- **签名地址的过期时间没有精确测出**（只验证了 ≥3 分钟）。若用户长时间停留在
  播放页后拖动到未缓冲区间，可能遇到 403/410；此时前端会提示重试，
  重试请求带 `fresh=1` 重新解析，不会一直失败。
- 播放器页按集索引取流（`/player/<sid>/<ep>`，从 0 开始）。当前播放页默认取第 0 集，
  多集切换 UI 尚未实现。
- `extractStreams` 只认 `main_url` 一个字段，未覆盖多清晰度；够用但非最优。
- 条目没有单集时长时，卡片与播放页用 `episodes_text` 兜底。
  采集侧若能拿到时长，写入 `duration_text` 字段即可自动展示。
