## 一、项目总览与定位

`F:\项目002` **不是一个单一应用**，而是一个以「企业级 SaaS 融合架构」为主题的**参考实现工作区**，由三份配套文档统一定义边界与选型：

| 文档 | 作用 |
|---|---|
| `项目技术背景与能力需求说明.md` | **Standing Context（边界约束）**：业务领域、技术选型、NFR 指标、代码助手守则 |
| `企业级SaaS技术架构蓝图.html` | 架构蓝图总览 |
| `技术路线选型决策指南.html` | 选型决策指南 |

工作区下含 **两个代码子项目**，二者在概念与运行上通过 WordPress 插件衔接：

1. **`saas-enterprise-monorepo`** — 四栈融合的**微服务骨架**（Go 网关 / Java 业务 / Python AI / TS BFF），可 `docker compose` 运行。
2. **`wordpress/`** — 标准 **WordPress 6.x 核心**（CMS/门户），唯一业务自定义是插件 **`saas-aggregator`**，它把 monorepo 暴露的 5 类后端能力聚合进 WordPress 统一展示 —— 是 monorepo 的「平行展现层/门户」。

> 关键认知：文档规划的展现层是 React/Vue + NestJS BFF；本工作区里**展现层有两套并存** —— `bff-web`（NestJS 雏形）与 `wordpress/saas-aggregator`（WordPress 门户），二者都调用同一套后端服务。

## 三、子项目 A：`saas-enterprise-monorepo`

### 模块清单

| 目录 | 技术 | 角色 | 对外端口 |
|---|---|---|---|
| `gateway-go/` | Go · Gin + gorilla/websocket + grpc | 接入层网关 | 8080 (HTTP/WS)，gRPC 调用 50051/50052 |
| `service-java/` | Java · Spring Boot | 业务应用层（订单/合规） | 8081 (HTTP)，50051 (gRPC) |
| `ai-python/` | Python · FastAPI | 智能层（LLM/RAG） | 8000 (HTTP)，50052 (gRPC) |
| `bff-web/` | TS · NestJS | 展现层 BFF 聚合 | 3000 (HTTP) |
| `proto/` | protobuf | 跨语言 gRPC 契约 + 生成配置 | — |
| `istio/` | YAML | 生产 Service Mesh 清单 | — |
| 根 `*.yml/.yaml/.sql/Makefile` | — | 编排/可观测/数据库初始化 | — |

### 3.1 gateway-go（接入层）
- **`main.go`** — 中间件链 `auditLogger → authAndTenant → rateLimit`；路由注册；`/ws` WebSocket 回显；初始化 gRPC 客户端与 OTel。
  - `auditLogger`：审计日志（ts/method/path/tenant/status/latency），独立通道。
  - `authAndTenant`：缺失 `Authorization` 或 `X-Tenant-Id` 即拒绝（合规默认开启）。
  - `rateLimitMiddleware`：按 IP 简单计数限流。
- **`handlers.go`** — `orderHandler`（gRPC 调 Java 订单）、`ragHandler`（gRPC 调 Python RAG）；均带 OTel span + `WithTenant` 透传。
- **`internal/grpc/client.go`** — `Clients` 聚合 Order/Ai 客户端；`WithTenant(ctx, id)` 把租户写入 gRPC metadata（行级隔离随调用传播）。
- **`internal/otel/otel.go`** — OTel SDK 初始化（OTLP 上报）。
- **依赖**：`service-java`(gRPC 50051)、`ai-python`(gRPC 50052)、`bff-web`(HTTP 3000)、`otel-collector`。

### 3.2 service-java（业务应用层）
- **`controller/OrderController.java`** — REST `/api/orders`（GET 列表、POST 创建，幂等键走 `Idempotency-Key` 头）。
- **`service/OrderService.java`** — `@Transactional` 强一致写；**幂等**：`findByTenantIdAndIdempotencyKey` 命中则返回已有单；两个 `createOrder` 重载（REST 用 / gRPC 用，分↔元换算）。
- **`repository/OrderRepository.java`** — JPA，按租户+幂等键查询。
- **`model/Order.java`** — 订单实体。
- **`tenant/TenantContext.java` + `TenantFilter.java`** — 从 `X-Tenant-Id` 提取写入 ThreadLocal，请求结束清理（**行级隔离基础**）。
- **`audit/ComplianceAuditAspect.java`** — `@AfterReturning` 切面，对所有 controller 方法留痕（tenant+action，不记敏感字段）。
- **`grpc/GrpcOrderService.java`** — 实现 `OrderServiceGrpc`，复用同一 `OrderService` 业务逻辑（gRPC↔REST 共享领域逻辑）。
- **`resources/application.yml`** — 数据源 / Redis / OTel 配置；`pom.xml`：Spring Boot、JPA、devh-grpc、AspectJ、OTel。
- **依赖**：PostgreSQL、Redis、otel-collector；被 `gateway-go`(gRPC) 与 `bff-web`(HTTP) 调用。

### 3.3 ai-python（智能层）
- **`app/main.py`** — FastAPI；`lifespan` 启动时 `db.init_db()` + 同进程拉起 gRPC；合规工具 `sanitize_input`（输入脱敏）、`compliance_check`（输出拦截黑名单）、`require_tenant`（租户校验）；接口 `/api/ai/llm`、`/rag`、`/index`、`/analyze`、`/health`。
- **`app/db.py`** — SQLAlchemy + pgvector；`KnowledgeChunk` 表（tenant_id + content + vector）；`init_db`（建 vector 扩展+建表+播种）；`similarity_search`（余弦 `<=>` 检索，租户过滤）。
- **`app/model_gateway.py`** — `ModelGateway` 抽象（embed/complete）；`PrivateGateway`（本地确定性伪嵌入，离线可跑）vs `CloudGateway`（OpenAI 兼容）；`get_gateway()` 按 `OPENAI_API_KEY` 切换（**私有化/多云切换**）。
- **`app/grpc_server.py`** — 实现 `AiService`（gRPC），单进程同启 HTTP+gRPC。
- **依赖**：PostgreSQL(pgvector)、otel-collector、RabbitMQ（`/analyze` 异步预留）；被 `gateway-go`(gRPC) 与 `bff-web`(HTTP) 调用。

### 3.4 bff-web（展现层 BFF）
- **`main.ts` / `app.module.ts` / `app.controller.ts`** — NestJS 引导与装配。
- **`proxy.service.ts`** — `ProxyService`：`getOrders` 调 Java `/api/orders`、`rag` 调 Python `/api/ai/rag`，统一透传 `X-Tenant-Id`。
- **依赖**：`service-java`(HTTP 8081)、`ai-python`(HTTP 8000)；被 `gateway-go` 反向代理。

### 3.5 proto/（契约）
- `order.proto`（`api.order.v1`）：`OrderService{CreateOrder,GetOrder}` + 消息（tenant_id / product / amount分 / idempotency_key）。
- `ai.proto`（`api.ai.v1`）：`AiService{Chat,Rag}` + 消息（references 字段用于**引用溯源**）。
- `Makefile` + `buf.gen.go.yaml`：构建期生成三栈桩（不入库）。

### 3.6 基础设施 / 运维
- `docker-compose.yml` — 本地编排 PG(pgvector)+Redis+RabbitMQ+4 服务+otel-collector+Jaeger。
- `db-init/01-enable-vector.sql` — 启用 vector 扩展。
- `otel-collector-config.yaml` — OTLP 采集 → Jaeger。
- `istio/gateway.yaml` + `destination-rule.yaml` — 生产 HTTPS 入口、mTLS、连接池限流、outlierDetection 熔断。

## 四、子项目 B：`wordpress/` + 插件 `saas-aggregator`

`wordpress/` 本身是**标准 WordPress 6.x 核心**（`wp-admin`、`wp-includes`、`wp-config-sample.php` 等）+ 默认主题（twentytwentythree/four/five）+ 默认插件（akismet、hello）。**唯一业务自定义**在 `wp-content/plugins/saas-aggregator/`（19 个文件）。

### 4.1 插件职责
把 monorepo 暴露的 **5 类后端能力**聚合到 WordPress 统一展示：网关状态 / 业务核心 / AI 洞察 / 决策分析 / 合规审计。支持**短代码 + Gutenberg 区块 + 后台设置 + 缓存 + 演示模式**。

## 五、模块依赖与调用关系

### 5.1 数据流（经网关）
```
浏览器 → gateway-go(:8080)
          ├─ /api/orders      ──gRPC──▶ service-java(:50051) ──▶ PostgreSQL
          ├─ /api/ai/rag      ──gRPC──▶ ai-python(:50052)    ──▶ pgvector
          ├─ /api/ai/*,/bff/* ──代理──▶ ai-python(:8000)/bff-web(:3000)
          └─ /ws              ──WebSocket 回显
各服务 ──OTel SDK──▶ otel-collector(:4317) ──▶ Jaeger(:16686)   # trace 随 gRPC metadata 传播
```

### 5.2 BFF 流
```
前端 → bff-web(:3000) ──HTTP──▶ service-java(:8081) / ai-python(:8000)   # 透传 X-Tenant-Id
```

### 5.3 WordPress 门户流
```
访客 → WP 页面 [saas_aggregator 短代码/区块]
     → SAAS_Agg_Frontend::render()
     → SAAS_Agg_Provider_Manager::aggregate()
     → 各 Provider::fetch_items()
          ├─ demo_mode=yes 且未配置 → demo_items() 模拟数据
          └─ 已配置 → SAAS_Agg_API_Client 调 monorepo /api/v1/...（松耦合 HTTP）
     → SAAS_Agg_Cache(Transients，stale 回退)
     → templates/aggregator-view.php 渲染
```

### 5.4 依赖方向（解耦原则：跨语言走 gRPC/HTTP，禁止库耦合）
- `gateway-go` → `service-java`(gRPC) / `ai-python`(gRPC) / `bff-web`(HTTP) / `otel-collector`
- `service-java` → PostgreSQL / Redis / otel-collector（被 gateway、bff 调用）
- `ai-python` → PostgreSQL(pgvector) / otel-collector / RabbitMQ(预留)（被 gateway、bff 调用）
- `bff-web` → `service-java` / `ai-python` (HTTP)
- `wordpress/saas-aggregator` → 外部 HTTP 调 monorepo 端点（松耦合，**演示模式可不依赖后端**）

## 六、可复用公共组件 / 工具 / 配置

### 6.1 跨服务共享（monorepo）
- **`proto/` 契约**：唯一接口真相源，三栈共用。
- **OTel 初始化模式**：各服务独立但同源（Go `internal/otel`、Java OTel SDK、Python OTel SDK）。
- **租户上下文透传**：`gateway-go.WithTenant(metadata)` → `service-java TenantFilter/TenantContext` → 行级隔离；Python `require_tenant`。
- **合规守则落地**（同源原则，文档§8）：Go 审计日志、Java `ComplianceAuditAspect`、Python `sanitize_input/compliance_check`、WP 密钥脱敏+错误日志。

### 6.2 高内聚可复用组件（saas-aggregator 插件）
- `SAAS_Agg_API_Client` — HTTP 客户端封装（超时/鉴权/错误/脱敏）。
- `SAAS_Agg_Cache` — 带 stale 回退的缓存（hit/fresh/stale）。
- `SAAS_Agg_Provider` 抽象基类 + `Provider_Interface` — 模板方法（do_fetch + normalize + cache + demo）。
- `SAAS_Agg_Provider_Manager` — 调度中心 + `apply_filters` 扩展点（开闭原则）。
- PSR-4 风格 autoloader、集中配置默认值合并。

### 6.3 配置模块
- **根级**：`docker-compose.yml`、`otel-collector-config.yaml`、`istio/*.yaml`、`db-init/*.sql`、`Makefile`、`proto/*.proto`、`buf.gen.go.yaml`。
- **各服务 env**：由 compose 注入（PG/Redis/OTel 地址等）。
- **WP 插件**：`saas_aggregator_settings` option + 默认值合并（`saas_agg_get_settings()`）。

## 八、关键约束与后续演进（注意事项）

1. **端点对齐问题**：插件默认调用的 `/api/v1/gateway/status`、`/api/v1/business/summary`、`/api/v1/ai/insights`、`/api/v1/analytics/dashboard`、`/api/v1/compliance/status` 与 monorepo 当前实际暴露的端点（`/api/orders`、`/api/ai/rag` 等）**命名不一致**；当前靠 `demo_mode` 兜底展示模拟数据。接入真实后端需在插件设置填入 base_url 并**对齐契约**。
2. **gRPC 桩构建期生成**：`make proto-*` / `mvn generate-sources` 在镜像 Dockerfile 内置；本地未实际编译，仅做结构核对。
3. **演进路线（README 标注）**：Java 引入 Seata 分布式事务、Sentinel 限流；Python `/analyze` 真实接 Celery+RabbitMQ；网关加 JWT 解析 + 租户配额；建 OpenAPI 契约仓库；GitOps 发布。
4. **WordPress 版本较新**（含 twentytwentyfive 主题），作为 CMS/门户层运行，与 BFF 展现层并存。
5. **敏感性**：所有自定义代码均落实「密钥不落明文日志、租户行级隔离、合规留痕」原则，与根文档§8 守则一致。
