## 一、总体开发思路

### 1.1 一条不可越界的红线

整个项目的第一原则：**WordPress 核心（`wp-admin/`、`wp-includes/`、根目录受控文件）一个字节都不改。**

这不是口头承诺，而是被拆成了三层可执行的保证：

| 层级 | 保证方式 | 落地手段 |
|---|---|---|
| **开发层** | 需求只用官方扩展机制实现 | 子主题、自定义插件、钩子、REST API、区块、短代码 |
| **校验层** | 每次交付都做核心完整性比对 | `scripts/verify-core.php` 对账官方 checksums（4171 条） |
| **部署层** | 运行时根本没有可写的核心 | 容器里核心来自镜像层，宿主机只挂载 `wp-content` 与 `wp-config.php` |

第三层是关键：即使有人想改核心，在生产容器里也改不了——这不是纪律问题，是拓扑问题。

### 1.2 功能落位的判断准则

拿到一个需求，先问三个问题，答案决定它落在哪里：

```
这个功能是「表现形态」还是「业务能力」？
    │
    ├─ 表现形态（长什么样 / 结构怎么排）────→ 子主题
    │      · 独立版式 → 页面模板（page-xxx.php）
    │      · 局部样式微调 → style.css
    │      · 加载脚本样式 → functions.php + wp_enqueue_*
    │
    └─ 业务能力（数据从哪来 / 谁能访问）────→ 自定义插件
           · 与主题解耦，换主题不丢功能
           · 可独立启停、独立升级
```

**为什么这么切？** 主题负责"看起来怎么样"，插件负责"能做什么"。如果业务能力写进主题，用户一换主题整个站点就废了——这是 WordPress 二次开发最常见的坑。本项目把聚合能力全部放在 `saas-aggregator` 插件里，子主题只做展示，两者通过**短代码 + 区块 + REST 接口**通信，互不依赖。

### 1.3 数据存放的判断准则

> 用户要求："优先复用 postmeta/options 或规范建表"

翻译成可执行的决策树：

```
数据规模 & 访问模式？
    │
    ├─ 少量配置项（低频读写、需要跨版本合并）──→ wp_options
    │      本例：插件全部设置项存在 saas_aggregator_settings
    │
    ├─ 依附于内容实体的扩展字段 ──────────────→ postmeta / user_meta
    │      本例：页面模板 _wp_page_template、租户 ID saas_agg_tenant_id
    │
    ├─ 临时结果（可重建、有过期时间）─────────→ Transients API
    │      本例：聚合结果缓存、REST 限流计数
    │
    └─ 高频追加写、需按维度检索、需定期清理 ──→ 规范自建表
           本例：wp_saas_agg_logs 审计流水
```

**唯一的自建表为什么必须存在？** 审计日志是"每次调用都追加一行、按时间和租户检索、定期清理 30 天前"的流水数据。塞进 `wp_options` 会让这张本就最热的表雪上加霜；塞进 `postmeta` 会污染内容查询。这是 WordPress 官方文档明确认可的自建表场景。

即便如此，建表也严格遵循原生规范（详见下文 2.6）。

### 1.4 渐进增强与优雅降级

聚合功能依赖外部微服务，外部服务挂了不能让站点一起挂。设计上做了三层降级：

```
真实网关可用 ──→ 拉真实数据
    ↓ 失败 / 未配置
Demo 模式数据 ──→ 展示结构完整的示例数据（默认出厂状态）
    ↓ 插件未启用
静态提示       ──→ 页面仍可正常渲染，只是聚合区块显示提示
    ↓ JS 不可用
服务端渲染兜底 ──→ 短代码与区块在服务端就输出内容，JS 只做刷新
```

这个设计让"演示环境 / 开发环境 / 生产环境"用同一套代码，只靠配置项切换，不需要维护三份代码。

## 二、所用扩展点全清单

### 2.1 子主题（`themes/slstyle-child/`）

| 扩展点 | 位置 | 作用 |
|---|---|---|
| 子主题机制（`Template:` 头） | `style.css` | 继承父主题 slstyle，父主题升级不影响子主题改动 |
| `wp_enqueue_scripts`（优先级 5） | `functions.php:35` | 补挂父主题样式，保证子主题启用后父样式仍在 |
| `wp_enqueue_scripts`（优先级 20） | `functions.php:90` | 仅在加载看板模板时按需加载 `dashboard.js`，其他页面不背这个请求 |
| `after_setup_theme`（优先级 11） | `functions.php:56` | 主题支持项声明，晚于父主题执行以覆盖父级设定 |
| `body_class` 过滤器 | `functions.php:137` | 按当前模板追加语义化 class，供 CSS 精确命中 |
| 页面模板层级 | `page-dashboard.php` | 用 WordPress 原生的 `page-{slug}.php` 模板层级，后台可直接选择 |

**关于"子主题必须重新 enqueue 父样式"**：这是新手最常踩的坑。启用子主题后 WordPress 只加载子主题的 `style.css`，父主题样式不会自动带上。本项目在 `functions.php` 里用 `wp_enqueue_style()` 显式挂回父样式，并且**优先级设为 5**（早于大多数插件），避免被覆盖。

### 2.2 自定义插件：激活 / 停用 / 卸载生命周期

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `register_activation_hook()` | `saas-aggregator.php:99` | 激活时建表 + 注册定时任务 |
| `register_deactivation_hook()` | `saas-aggregator.php:120` | 停用时清理定时任务，**保留数据** |
| `uninstall.php` | `uninstall.php` | 仅在后台"删除插件"时触发，清表、清 option、清计划任务 |

**为什么停用不删数据？** 停用是临时动作（排查冲突、灰度回滚），删了数据就找不回来了。真正的数据清理只在用户明确执行"删除"时发生——这是 WordPress 官方倡导的生命周期语义。

**为什么不能直接用 SQL 改 `wp_options` 里的 `active_plugins`？** 那样改只是翻了个状态位，`register_activation_hook` 不会触发，表和定时任务都不会建立。`scripts/wp-bootstrap.php` 一律走 `activate_plugin()` API，与后台点击"启用"完全等价。

### 2.3 REST API

| 路由 | 方法 | 权限控制 | 用途 |
|---|---|---|---|
| `/wp-json/saas-aggregator/v1` | GET | 公开 | 接口索引 |
| `/sources` | GET | 需鉴权 | 数据源清单 |
| `/data` | GET | 需鉴权 | 拉取聚合数据（带缓存） |
| `/health` | GET | 公开 | 健康检查探针 |
| `/cache/flush` | POST | 需 `manage_options` | 手动清缓存 |
| `/logs` | GET | 需 `manage_options` | 审计日志查询 |

全部通过 `register_rest_route()` 注册，自动获得：
- `WP_REST_Request` / `WP_REST_Response` 的参数校验与序列化
- `permission_callback` 统一鉴权（匿名访问返回 401，实测已验证）
- `/wp-json` 自动发现与 Schema 描述
- 可被 Application Passwords / Cookie / JWT 等所有 WordPress 标准鉴权方式接入

**限流**：基于 Transients 计数，默认 60 次/分钟，可用 `saas_agg_rest_rate_limit` 过滤器调整。

### 2.4 区块（Gutenberg）

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `block.json` | 插件根目录 | 声明式元数据（名称、属性、脚本、编辑器入口），WordPress 推荐做法 |
| `register_block_type()`（`init` 钩子） | `class-frontend.php:33` | 注册区块，带 `render_callback` |
| 动态渲染 | `render_callback` | 服务端渲染，保证区块在 REST 输出与无 JS 环境下都可用 |

### 2.6 数据表规范

`wp_saas_agg_logs` 的建表严格遵守 WordPress 数据表规范：

```php
global $wpdb;
$table   = $wpdb->prefix . 'saas_agg_logs';           // ① 跟随站点表前缀（多站点 / 自定义前缀都成立）
$charset = $wpdb->get_charset_collate();              // ② 跟随站点字符集，不硬编码 utf8mb4
require_once ABSPATH . 'wp-admin/includes/upgrade.php';
dbDelta( $sql );                                      // ③ 增量升级，重复执行安全
update_option( 'saas_aggregator_db_version', '1.0.0' ); // ④ 版本号存 option，避免每次请求跑 DDL
```

四个约定一个都不能少，原因：

| 约定 | 不遵守的后果 |
|---|---|
| ① `$wpdb->prefix` | 多站点或自定义前缀站点直接找不到表 |
| ② `get_charset_collate()` | 与站点字符集不一致，emoji 存不进去或 JOIN 时索引失效 |
| ③ `dbDelta()` | 版本升级时加字段要写手工迁移脚本，容易出错 |
| ④ 版本号存 option | 每次请求都执行 `SHOW COLUMNS`，前台性能被拖垮 |

**DDL 执行时机也做了收敛**：只在后台（`is_admin()`）且版本号不一致时才检查升级，前台请求永远不碰 DDL。

### 2.7 定时任务与缓存

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `wp_schedule_event()` | `saas-aggregator.php:112` | 每日清理过期审计日志 |
| `wp_next_scheduled()` | `saas-aggregator.php:111` | 注册前查重，避免重复排程 |
| `wp_clear_scheduled_hook()` | `uninstall.php:22` | 卸载时彻底清理 |
| Transients API | `class-cache.php`、`class-rest.php` | 聚合结果缓存、限流计数 |

**为什么用 WP-Cron 而不是系统 crontab？** WP-Cron 是 WordPress 原生能力，零部署依赖、可后台查看管理、卸载时自动清理。代价是依赖站点访问触发——因此生产环境建议按部署文档把系统 crontab 指向 `wp-cron.php` 并禁用 `DISABLE_WP_CRON` 触发式执行。

### 2.9 官方 drop-in 扩展点

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `db-error.php` | `wp-content/db-error.php` | 数据库连接失败时的诊断页 |

这是 WordPress 官方认可的 drop-in，由 `wpdb::db_connect()` 内部 `require`，**完全不触及核心**。本项目用它替代了核心默认的"建立数据库连接时出错"空白页，输出错误号、错误详情、连接目标，并落盘到 `wp-content/db-error-detail.log`。

> ⚠️ 实现上有两个必须注意的坑（本次已踩并修复）：
> 1. 该文件执行时 `$wpdb` 全局变量**尚未赋值**，必须用 `$this` 取实例；
> 2. 绝不能调用 `esc_html()` 等会访问数据库的 WP 函数——数据库已经挂了，会递归 fatal。

### 3.2 修改文件明细

#### ① `router.php` —— 本次最关键的缺陷修复

**问题**：PHP 内置服务器下访问 `/wp-admin/install.php` 无限 302 重定向到自身，安装流程完全走不下去。

**根因**：Windows 下 `realpath()` 返回反斜杠路径（`D:\...\public\wp-admin\install.php`），而 `$docroot` 是用正斜杠拼出来的。`strpos($target, $docroot) === 0` 这个前缀判断恒为 `false`，于是**所有真实存在的文件都被误判为不存在**，统统转发给 `index.php`；`wp_not_installed()` 又把请求重定向回 `install.php`，形成死循环。

**修复**：引入路径归一化，消除平台差异。

```php
function wp004_normalize_path( $path ) {
    $path = str_replace( '\\', '/', (string) $path );
    return rtrim( $path, '/' );
}
$docroot = wp004_normalize_path( realpath( __DIR__ . '/public' ) );
$target  = wp004_normalize_path( realpath( $docroot . $path ) );
if ( false !== $target && is_file( $target ) && 0 === strpos( $target, $docroot . '/' ) ) {
    return false;   // 真实文件：交给内置服务器直接返回
}
```

**效果**：`install.php` 从 302 死循环变为 200，安装流程打通。

#### ② `public/wp-content/db-error.php`

新增并修正两次：
- 初版调用 `esc_html()` → 数据库已挂，`esc_html()` 间接触发 `get_option()` 访问数据库 → 递归 fatal。改用原生 `htmlspecialchars()`。
- 初版用 `global $wpdb` 取实例 → 该文件由 `wpdb::db_connect()` 内部 `require`，此时 `$wpdb` 尚未赋值，恒显示"实例不可用"。改用 `$this`。

#### ④ `saas-aggregator.php` —— 模块引导时序修复

**问题**：所有模块（设置页/前台/租户/数据层/REST）原本挂在一个 `plugins_loaded` 的闭包上。当插件在**同一请求内被激活**时（CLI 初始化脚本、程序化调用 `activate_plugin()`），`plugins_loaded` 早已触发过，闭包永远不会执行，结果是 REST 路由一条都没注册。

**修复**：把闭包改成具名函数 `saas_agg_bootstrap()`，并兼容两种时序：

```php
if ( did_action( 'plugins_loaded' ) || doing_action( 'plugins_loaded' ) ) {
    saas_agg_bootstrap();                        // 已触发过 → 立即引导
} else {
    add_action( 'plugins_loaded', 'saas_agg_bootstrap', 10 );
}
```

函数内用 `static $bootstrapped` 兜底，防止重复实例化。

### 3.2b 真实联调后追加的修改（⑪~⑭）

这一组改动全部源自**把插件接到本机 `mixmlaal-*` 微服务栈上实跑**——只有真跑才会暴露的契约问题。详见 `docs/03-待确认项.md` 第 1 节。

#### ⑪ `saas-aggregator.php` —— 电商数据源独立服务地址 + 设置结构迁移

**问题**：6 个数据源共用一个默认 `base_url`（Go 网关），但 `/api/products` 实测**不在网关上**：

```
http://gateway-go:8080/api/products   → 404 page not found
http://node-api:3001/api/products     → 200，真实商品数据
```

**修复**：给 `ecommerce` 单独指定 `base_url`，走新增常量 `SAAS_AGG_NODE_API_URL`。因为默认设置是「`$meta` 覆盖通用默认值」的 `array_merge` 结构，只需在 `ecommerce` 的元数据里带上 `base_url` 即可，其余 5 个源不受影响。

**配套难点**：`saas_agg_get_settings()` 用 `wp_parse_args( 已存值, 默认值 )` 合并，**已存值优先**。这本是刻意为之（用户改过的配置不能被插件升级覆盖），但副作用是——老站点会一直沿用错误的历史地址，改默认值救不了它。

因此加了一套**设置结构（schema）迁移**：

```php
define( 'SAAS_AGG_SETTINGS_SCHEMA', '2' );           // 与插件版本分开维护
define( 'SAAS_AGG_SETTINGS_SCHEMA_OPTION', 'saas_aggregator_settings_schema' );

function saas_agg_maybe_upgrade_settings() { /* 版本比对 + 定向纠正 */ }
add_action( 'plugins_loaded', 'saas_agg_maybe_upgrade_settings', 9 );
```

迁移原则：**只纠正仍等于旧默认值的条目，用户手动改过的一律不动。**

挂载在 `plugins_loaded` **优先级 9**（早于模块引导的 10），保证任何模块读到设置时迁移已完成；同时在 `saas_agg_bootstrap()` 与激活钩子里各兜一次——因为若插件是在请求中途被 `activate_plugin()` 激活的，`plugins_loaded` 早已触发过（与 ④ 同一个坑）。

#### ⑫ `includes/class-provider-interface.php` —— 兼容 Node 层的响应包装

**问题**：Node 层与 Python 层的响应包装不同：

```jsonc
// Python 层（gateway-go / ai-python）
{ "tenant": "wp004-test", "items": [ {...} ] }

// Node 层（node-api）
{ "code": 200, "msg": "成功", "data": { "products": [ {...} ] } }
```

原 `normalize_response()` 把 `data` 当列表遍历，遍历到的是 `{"products":[...]}` 这一整块，逐条归一化后 `title`/`value` **全为空**。

**修复**：新增 `unwrap_data_envelope()`——单键且值为数组时拆开信封，数字键（已是列表）或多键（无法判定取哪个）则原样返回。这是对**基类**的加固，所有走 `data` 包装的数据源都受益。
