## 二、已确认事项（附实测证据）

### 1. 6 个数据源的真实网关地址与鉴权凭据 ✅

**不再需要你提供文档——我直接探测了本机微服务栈，并跑通了真实联调。**

#### 1.1 网关鉴权契约（已确认）

对 `gateway-go:8080` 做无凭据请求，返回：

```
HTTP 401
缺少 Authorization 或 X-Tenant-Id 头
```

而插件的 `class-api-client.php` 恰好就是同时发送这两个头，代码注释里也写着"网关不校验令牌值"。**两边契约本来就对得上**，鉴权方式确认为：

```
Authorization: Bearer <token>
X-Tenant-Id:   <tenant>
```

且网关**只校验头是否存在，不校验令牌值**（内网可信模型）。

#### 1.2 数据源路径契约（已确认）

拉取 `ai-python:8000` 的 OpenAPI 文档（"智能层 AI 服务 v0.2.0"），实际暴露的路径为：

```
/health
/api/ai/llm
/api/ai/rag
/api/ai/index
/api/ai/analyze
/api/ai/tasks/{task_id}
/api/analytics/dashboard
/api/compliance/status
```

参数统一为 header `X-Tenant-Id`（非必填），**未声明任何安全方案**。

与插件内置默认值比对：

| 数据源 | 插件默认路径 | 实测结果 |
|---|---|---|
| `ai_insights` | `/api/ai/rag` | ✅ 完全命中（需 POST，GET 返回 405） |
| `analytics` | `/api/analytics/dashboard` | ✅ 完全命中 |
| `compliance` | `/api/compliance/status` | ✅ 完全命中 |
| `gateway_status` | `/api/gateway/status` | ✅ 网关 200，返回 `{"items":[{"status":"ok","title":"网关可用性",...}]}` |

#### 1.4 顺带发现并修复的两个真实契约缺陷

**缺陷 A：电商数据源地址指错了服务**

```
http://127.0.0.1:8080/api/products   → 404 page not found   （Go 网关上没有）
http://127.0.0.1:3001/api/products   → 200，真实商品数据     （Node.js BFF 上有）
```

`/api/products` 从来就不在 Go 网关上，而插件的 6 个源共用一个默认 `base_url`（网关）——这是原实现的错。已改为：电商源单独走 `SAAS_AGG_NODE_API_URL`（默认 `http://node-api:3001`），其余 5 个仍走 `SAAS_AGG_GATEWAY_URL`。

> 因为设置是「已存值优先」合并的，光改默认值救不了老站点，所以配套加了一次性迁移（见 `docs/02` 的改动清单）。迁移只纠正"仍等于旧默认值"的条目，**用户手动改过的地址一律不动**。

**缺陷 B：Node 层的响应包装与 Python 层不同**

```jsonc
// Python 层（gateway-go / ai-python）
{ "tenant": "wp004-test", "items": [ {...}, {...} ] }

// Node 层（node-api）
{ "code": 200, "msg": "成功", "data": { "products": [ {...}, {...} ] } }
```

`data` 里再套了一层**具名集合**。原 `normalize_response()` 把 `data` 当列表遍历，遍历到的是 `{"products":[...]}` 这一整块，逐条归一化后 `title`/`value` 全空。已新增 `unwrap_data_envelope()`：单键且值为数组时拆开信封，其余情况原样返回。这是对**基类**的通用加固，所有走 `data` 包装的数据源都受益。

#### 1.5 现在的默认行为

`demo_mode` **默认关闭**（`global.demo_mode = 'no'`），激活即接真实后端。若要回到演示数据，在「设置 → SaaS 聚合器」里勾上即可，不需要改代码。

## 三、仍需你拍板的事项

### 3. 租户体系的权威来源 🔴（**最需要你拍板的一条**）

**代码里能看到什么**

```
WordPress 用户 meta: saas_agg_tenant_id  ──→  请求头 X-Tenant-Id  ──→  网关
```

在「用户资料」页加了自定义字段（`show_user_profile` / `edit_user_profile` 钩子），管理员可给每个用户绑定租户 ID。

**实测补充**：网关接受任意 `X-Tenant-Id` 值（用 `wp004-test` 打通了全部 6 个源），说明**租户隔离不是网关做的**，而是下游服务按这个头分流。这让"权威来源"的问题更关键——**谁来保证这个头的值是对的？**

**需要你确认**

1. **租户的权威来源是谁？**
   - 方案 A：WordPress 是权威，租户在这里创建，下游跟着走
   - 方案 B：微服务侧是权威，WordPress 只是缓存一份映射
   - 方案 C：有独立 IAM / 租户中心，两边都去同步
2. **未绑定租户的用户怎么处理？** 现在走默认租户 `default`，是否应该直接拒绝？
3. **租户 ID 的格式与校验规则**？现在只做了 `sanitize_text_field`，没有格式校验。
4. REST `/logs` 是否要按租户过滤？（表里有 `tenant_id` 字段，但查询未过滤）

**为什么这条最要紧**：租户是安全边界。实测证明网关不校验租户有效性——**只要 WordPress 侧的租户值错了，就会读到别人的数据，且网关不会拦**。

### 5. 是否需要对外开放的公开接口 🟡

**代码里能看到什么**：REST 路由默认全部需鉴权，但留了开关：

```php
$public = (bool) apply_filters( 'saas_agg_rest_public_read', false );
```

**需要你确认**

1. 前端是服务端渲染（主题模板里直接调），还是独立 SPA（需跨域调用）？
2. 若是 SPA：用 Application Passwords、JWT，还是自建 Token？
3. 公开接口限流阈值是否单独设？（现在读写共用 60 次/分钟）

**当前处理方式**：全部需鉴权（匿名返回 401，已验证）。前端走服务端渲染 + 同域 fetch。

---

### 6. 审计日志的保留期与合规要求 🟡

- 表 `wp_saas_agg_logs` 记录每次接口调用
- WP-Cron 每日清理，保留期由 `saas_agg_log_retention_days` 控制，**默认 30 天**
- 表里有 `tenant_id`、`ip`、`user_id`

**需要你确认**

1. 30 天够不够？有无合规要求（等保 / GDPR）要求更长或更短？
2. `ip` 与 `user_id` 属个人信息，是否需要脱敏？（顺带一提：实测 `compliance` 源显示下游已启用脱敏 rules 2，WordPress 侧日志是否要对齐？）
3. 是否归档而非直接删？
4. 日调用量预估？量大可能需要分区表或按月分表。

### 7. 多站点（Multisite）是否启用 🟡

所有建表都用了 `$wpdb->prefix`，代码层面已为多站点做好准备。

**需要你确认**：是否会开启？若开启，插件是「网络启用」还是「各站点独立启用」？网络启用时 `wp_saas_agg_logs` 会变成每站点一张，还需要额外的网络级设置页。

## 五、关于"反推 + 实测"的说明

这一版相比初版有个方法上的变化：**初版只做代码反推，这一版我直接去探测了运行环境**。

原因是第 1 项虽然是 🔴 阻塞项，但它属于"环境里客观存在、只是文档缺失"的事实，不是需要你做业务决策的选择题。这类问题问你反而低效——你还得回头翻配置。所以我先把能自己验证的验证掉，只把真正的**业务决策**（租户谁说了算、要不要写、要不要换门户）留给你。

结果是：10 项待确认收敛到 9 项，且其中最阻塞的一条已经变成"已接真实数据并跑通"，顺带还揪出两个只有真跑才会暴露的契约缺陷（电商地址指错服务、Node 层响应包装不同）。

**当前系统状态**：结构完整 **且数据为真**——6 个数据源全部对接本机微服务成功，同时保留一键切回 demo 的能力。
