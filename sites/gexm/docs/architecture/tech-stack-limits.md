## 1. 后端技术栈限制

### 1.1 Express.js 限制

| 限制点 | 限制描述 | 影响范围 | 严重程度 | 替代方案 |
|--------|----------|----------|----------|----------|
| 单线程并发瓶颈 | Node.js 单线程事件循环模型，CPU 密集型任务会阻塞整个服务 | 全平台后端服务 | 中 | 引入 Worker Threads 处理 CPU 密集任务；使用 Cluster 模式多进程部署 |
| 中间件生态碎片化 | Express 中间件质量参差不齐，安全和性能依赖第三方库 | 后端整体 | 中 | 精选成熟中间件，自建核心中间件；考虑迁移到 NestJS |
| 缺少内置依赖注入 | 无原生 DI 容器，模块间耦合度高，测试困难 | 后端架构 | 中 | 手动实现简单 DI 容器；迁移到 NestJS/TypeDI |
| TypeScript 兼容成本 | 当前为纯 JavaScript 项目，无类型安全，重构风险高 | 后端整体 | 高 | 逐步迁移 TypeScript；使用 JSDoc 补充类型注解 |

**代码证据**：
- 入口文件：`packages/server/src/app.js:45` - 纯 JS Express 应用
- 路由挂载：`packages/server/src/app.js:131-153` - 20+ 路由硬编码挂载，无 DI 容器
- 模块导入：`packages/server/src/models/orderModel.js:1-2` - CommonJS require 模式

### 1.2 SQLite 限制

| 限制点 | 限制描述 | 影响范围 | 严重程度 | 替代方案 |
|--------|----------|----------|----------|----------|
| 并发写入限制 | 单写多读架构，写操作串行化，高并发写入场景性能急剧下降 | 订单、支付、库存等核心业务 | 高 | 引入写队列；迁移到 PostgreSQL/MySQL；使用读写分离 |
| 大规模数据量性能衰减 | 单表数据量超过百万级后，查询性能明显下降 | 订单、日志、消息等表 | 中 | 分库分表；引入 Elasticsearch 做检索；迁移到分布式数据库 |
| 缺少高级数据库特性 | 无存储过程、触发器、视图、CTE 递归等高级特性 | 复杂业务逻辑 | 中 | 在应用层实现复杂逻辑；迁移到 PostgreSQL |
| 不支持分布式部署 | 文件型数据库，无法跨节点共享，水平扩展困难 | 多实例部署、容器化 | 高 | 迁移到客户端/服务器型数据库；使用 SQLite + 同步方案 |
| 连接池管理限制 | 单连接架构，无连接池概念，连接管理简单但受限 | 数据库访问层 | 低 | better-sqlite3 单连接已足够；迁移后使用连接池 |
| 动态类型系统 | 数据类型灵活但弱约束，类型错误只能在运行时发现 | 数据完整性 | 中 | 在应用层加强校验；引入 ORM 类型映射；迁移 TypeScript |

**代码证据**：
- 数据库初始化：`packages/server/src/models/index.js:15-27` - 单文件 SQLite，单连接
- 表数量：`packages/server/src/models/index.js:31-619` - 超过 30 张业务表
- WAL 模式：`packages/server/src/models/index.js:16` - 已启用 WAL 优化读并发
- 索引优化：`packages/server/src/models/index.js:159-448` - 大量索引优化查询

### 1.3 better-sqlite3 限制

| 限制点 | 限制描述 | 影响范围 | 严重程度 | 替代方案 |
|--------|----------|----------|----------|----------|
| 同步 API 阻塞风险 | 所有数据库操作都是同步的，大查询会阻塞事件循环 | 所有数据库交互 | 高 | 分批处理大查询；使用 Worker Threads 隔离数据库操作 |
| 异步处理模式缺失 | 无 Promise/async 支持，无法与异步生态无缝集成 | 数据库访问层 | 中 | 封装异步适配器；迁移到支持异步的数据库驱动 |
| 大事务响应阻塞 | 大事务执行期间服务完全无响应，请求排队积压 | 订单创建、批量操作 | 中 | 拆分大事务；引入消息队列异步处理；优化事务范围 |

**代码证据**：
- 同步查询：`packages/server/src/models/orderModel.js:19-20` - `db.prepare().get()` 同步调用
- 事务处理：`packages/server/src/services/orderService.js:201-261` - `db.transaction()` 同步事务
- 批量操作：`packages/server/src/services/orderService.js:202-223` - 循环内同步更新库存

### 1.4 JWT 认证限制

| 限制点 | 限制描述 | 影响范围 | 严重程度 | 替代方案 |
|--------|----------|----------|----------|----------|
| 即时吊销困难 | 无状态 Token 签发后无法即时作废，必须等待过期 | 安全、登出、权限变更 | 高 | 引入 Token 黑名单（Redis）；使用短有效期 + 刷新 Token；迁移到 Session |
| Token 体积与传输开销 | 携带用户信息的 JWT 体积较大，每次请求都要传输 | API 性能 | 低 | 精简 Token 载荷；使用 Redis 存储用户信息；考虑 Session |
| 刷新 Token 管理复杂 | 刷新 Token 存储、轮换、失效策略实现复杂 | 认证系统 | 中 | 引入专门的 Token 管理服务；使用 OAuth 2.0 框架 |
| 多设备登录限制 | 难以精确管理用户多端登录状态，无法强制下线指定设备 | 用户体验、安全 | 中 | 数据库存储 Token 与设备绑定；引入设备管理模块 |

**代码证据**：
- JWT 配置：`packages/server/src/config/index.js:7-12` - 访问 Token 24h，刷新 Token 7d
- 认证中间件：`packages/server/src/middleware/auth.js:15-17` - 仅验证签名，无吊销检查
- 刷新 Token 表：`packages/server/src/models/index.js:48-55` - 简单存储，无设备绑定
- 用户状态检查：`packages/server/src/middleware/auth.js:23-25` - 每次查询数据库验证用户状态

| 多端兼容功能折衷 | 为兼容多平台，必须使用各平台交集特性，无法充分利用平台能力 | 全部前端功能 | 中 | 按平台编写条件编译；牺牲部分平台支持 |

## 6. 功能实现限制

基于当前技术栈，以下功能实现成本高或不推荐实现：

### 6.1 复杂事务处理

| 项目 | 说明 |
|------|------|
| **限制描述** | SQLite 虽支持事务，但同步阻塞 + 单写架构，复杂事务（涉及多张表、大量数据）会严重影响并发性能 |
| **影响范围** | 订单、支付、库存、营销等涉及多表联动的业务 |
| **严重程度** | 高 |
| **替代建议** | 1. 简化事务范围，只保护关键操作<br>2. 引入消息队列做最终一致性<br>3. 迁移到 PostgreSQL 等支持高并发事务的数据库 |
| **代码参考** | `packages/server/src/services/orderService.js:201-261` - 订单创建事务 |

### 6.2 实时推送（WebSocket 规模）

| 项目 | 说明 |
|------|------|
| **限制描述** | 单机 WebSocket 连接数有限（几千到一万），且无法多实例共享连接状态 |
| **影响范围** | 聊天、通知、实时数据推送 |
| **严重程度** | 中 |
| **替代建议** | 1. 引入 Redis Pub/Sub 实现多实例消息同步<br>2. 使用专业 IM 服务<br>3. 限制并发连接数，超出降级为轮询 |

### 6.3 大数据量分析报表

| 项目 | 说明 |
|------|------|
| **限制描述** | SQLite 聚合查询性能有限，大数据量统计报表响应慢，且会阻塞正常业务查询 |

## 7. 总体评分与适用场景建议

### 7.1 技术栈选型总体评分

| 维度 | 评分 (1-10) | 说明 |
|------|-------------|------|
| **开发效率** | 7 | Express + uni-app 上手快，简单项目开发效率高 |
| **性能表现** | 5 | SQLite + 单线程在小规模下够用，高并发瓶颈明显 |
| **可扩展性** | 3 | 水平扩展困难，微服务化代价大 |
| **可维护性** | 5 | 无 TypeScript、测试不足，项目大了维护成本上升快 |
| **安全性** | 6 | 基础安全措施到位，但缺少企业级安全特性 |
| **部署运维** | 6 | 部署简单，但缺少监控、告警、备份等企业级方案 |
| **生态丰富度** | 7 | Express 和 Vue 生态丰富，但 uni-app 生态相对小 |
| **团队友好度** | 7 | 技术栈主流，招人容易，但深度人才少 |

**综合评分：5.8 / 10**

### 7.2 适用场景建议

#### ✅ 推荐场景

1. **小型创业项目 MVP**：快速验证想法，开发成本低，部署简单
2. **内部工具/管理系统**：用户量有限，功能复杂但并发不高
3. **个人/小团队项目**：维护成本可接受，技术栈简单
4. **原型/演示项目**：快速搭建可演示版本
5. **预期用户量 < 10 万**：SQLite + 单机部署足够支撑

#### ⚠️ 谨慎使用场景

1. **预期快速增长的产品**：需要提前规划数据库迁移方案
2. **涉及金融/交易的核心系统**：对数据一致性、并发要求高
3. **需要 7x24 高可用**：单点故障风险，需要额外设计高可用方案
4. **团队规模 > 10 人**：无类型系统、测试不足会放大协作成本

#### ❌ 不推荐场景

1. **高并发互联网产品**（>10 万日活）：性能瓶颈明显
2. **企业级 SaaS 服务**：多租户、水平扩展、微服务都不友好
3. **大数据/数据分析平台**：SQLite 分析能力不足
4. **对数据安全/合规要求极高**：审计、备份、权限管理不足

### 7.3 演进路线建议

如果项目预期会增长，建议按以下路线逐步演进：

**第一阶段（0-1000 用户）：当前架构**
- 保持现有技术栈
- 补充核心模块测试
- 完善监控和告警

**第二阶段（1000-10000 用户）：性能优化**
- 引入 Redis 缓存
- 引入消息队列处理异步任务
- 数据库优化（索引、查询优化）
- 补充 TypeScript 类型定义

**第三阶段（10000-100000 用户）：架构升级**
- 迁移到 PostgreSQL/MySQL
- 引入 NestJS 重构后端
- 前端迁移 TypeScript
- 完善 CI/CD 和自动化测试

**第四阶段（10 万+ 用户）：分布式架构**
- 微服务拆分（按领域）
- 引入服务治理框架
- 数据库分库分表
- 多活/异地容灾

---

> **总结**：GEXM 当前技术栈是典型的「小而美」方案，适合快速启动和小规模应用。它的优势是开发快、部署简单、学习成本低；劣势是扩展性有限、维护成本随规模上升快。如果预期用户量在几万以内，这是一个性价比很高的选择；如果预期会快速增长，建议尽早规划技术栈演进路线，避免后期积重难返。
