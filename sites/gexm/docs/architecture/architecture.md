# 架构设计文档

## 1. 系统概览

Gexm 全平台应用系统采用"一套代码，多端运行"的架构设计，基于 uni-app + Vue3 + Express.js 技术栈，实现移动端APP、多端小程序、H5网页、PC桌面端的全平台覆盖。系统集成了完整的商城功能和即时通讯能力。

### 1.1 系统组成

| 平台 | 技术方案 | 支持范围 | 代码复用率 |
|------|----------|----------|------------|
| 移动端 APP | uni-app + 原生插件 | iOS 12.0+, Android 8.0+ | ~90% |
| 小程序 | uni-app 多端编译 | 微信/支付宝/百度/抖音 | ~85% |
| PC 桌面端 | Electron + uni-app H5 | Windows 10+, macOS 10.14+, Ubuntu 18.04+ | ~80% |
| H5 网页 | uni-app H5 + PWA | Chrome/Firefox/Safari/Edge 最新两版 | ~95% |

### 1.2 设计目标

- **统一体验**: 各平台UI/UX保持一致，遵循统一的设计系统
- **高效开发**: 一套代码多端运行，最大化代码复用
- **性能优先**: 各端性能指标达到行业标准
- **可扩展性**: 模块化架构，支持功能快速迭代
- **高可用性**: 完善的错误监控和容灾机制

## 3. 核心模块设计

### 3.1 用户认证模块

#### 3.1.1 功能特性

- 登录/注册/登出
- JWT + Refresh Token 双令牌机制
- 密码加密存储（bcryptjs）
- Token 自动刷新
- 多端会话管理

#### 3.1.2 认证流程

```
客户端                    服务端
  │                        │
  │─── POST /login ────────>│
  │   {username, password}  │
  │                        │─── 查询用户
  │                        │─── 验证密码
  │                        │─── 生成 Token
  │                        │
  │<─── {accessToken,       │
  │     refreshToken} ──────│
  │                        │
  │─── 请求 (带 Token) ────>│
  │                        │─── 验证 Token
  │                        │─── 处理请求
  │                        │
  │<─── 响应 ───────────────│
  │                        │
  │─── POST /refresh ─────>│
  │   {refreshToken}       │
  │                        │─── 验证 Refresh Token
  │                        │─── 生成新 Token
  │                        │
  │<─── {newToken} ────────│
```

#### 3.1.3 安全机制

| 机制 | 实现方式 |
|------|----------|
| 密码加密 | bcryptjs (10轮) |
| Token 签名 | HS256 算法 |
| Token 有效期 | Access 24h / Refresh 7d |
| 登录限流 | express-rate-limit |
| 注册限流 | express-rate-limit |

## 5. API 设计原则

### 5.1 设计规范

- 遵循 RESTful 设计规范
- 统一响应格式：`{ code, message, data, timestamp }`
- 统一错误码体系
- 分页查询标准化
- 认证信息通过 `Authorization` 头传递

### 5.2 响应格式

#### 成功响应

```json
{
  "code": 0,
  "message": "成功",
  "data": { ... },
  "timestamp": 1704067200000
}
```

#### 失败响应

```json
{
  "code": 2001,
  "message": "未登录或登录已过期",
  "data": null,
  "timestamp": 1704067200000
}
```

### 5.3 分页响应

```json
{
  "code": 0,
  "message": "成功",
  "data": {
    "list": [...],
    "page": 1,
    "pageSize": 20,
    "total": 100,
    "totalPages": 5
  },
  "timestamp": 1704067200000
}
```

### 5.4 错误码体系

| 范围 | 分类 |
|------|------|
| 1000-1999 | 通用错误 |
| 2000-2999 | 认证授权错误 |
| 3000-3999 | 业务逻辑错误 |
| 4000-4999 | 资源操作错误 |
| 6000-6999 | 安全相关错误 |

## 6. 安全设计

### 6.1 认证安全

- JWT 令牌认证
- Refresh Token 刷新机制
- 密码 bcrypt 加密（10轮）
- 登录失败限流（5分钟内最多10次）
- 注册限流（1小时内最多5次）

### 6.2 接口安全

- CORS 跨域控制（生产环境白名单）
- 请求频率限制（15分钟内最多100次）
- 输入参数校验
- SQL 注入防护（参数化查询）
- XSS 攻击防护
- Helmet 安全头

### 6.3 数据安全

- 敏感数据加密存储
- HTTPS 传输加密
- 最小权限原则
- 数据备份机制

## 7. 性能优化策略

### 7.1 前端优化

- 代码分割与懒加载

## 9. 关键设计决策

### 9.1 选择 uni-app 的原因

- **跨端能力**: 一套代码支持多端运行
- **Vue 3 支持**: 现代化开发体验
- **生态成熟**: 丰富的插件和组件库
- **性能优异**: 编译到原生，性能接近原生应用

### 9.2 选择 SQLite 的原因

- **零配置**: 无需额外安装数据库服务
- **轻量级**: 适合中小规模应用
- **文件存储**: 便于备份和迁移
- **开发友好**: 快速启动和调试

### 9.3 JWT 认证方案

- **无状态**: 服务端无需存储会话
- **可扩展**: 支持分布式部署
- **灵活**: Token 可携带用户信息
- **安全**: 签名验证防篡改

### 9.4 WebSocket 实时通讯

- **低延迟**: 实时消息推送
- **双向通信**: 客户端和服务端互发消息
- **持久连接**: 减少请求开销
- **事件驱动**: 高效的消息处理
