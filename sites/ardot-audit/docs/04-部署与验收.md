# 第一部分 · 部署步骤

## 1.1 两条部署路径

| 路径 | 适用场景 | 数据库 | Web 服务器 | 复杂度 |
|---|---|---|---|---|
| **A. 本地开发** | 日常开发调试 | WSL 内 Docker MySQL | PHP 内置服务器 + `router.php` | 低 |
| **B. 容器栈** | 预发 / 生产 | `wp004-mysql` 容器 | nginx + php-fpm | 中 |

两套路径**共用同一份代码与同一套脚本**，靠环境变量切换，不存在"本地能跑线上跑不了"的情况。

## 1.2 路径 A：本地开发环境

### 前置条件

- Windows 11 + WSL2（Ubuntu 22.04）
- WSL 内已运行 dockerd，MySQL 容器在跑
- WSL 内 PHP ≥ 8.0（自带 8.1.2 即可，需 `mysqli`/`gd`/`zip`/`curl`）

### 步骤

```bash
# 1) 配置环境变量
cp .env.example .env        # 若没有 example 就直接编辑现有 .env
#   重点改：DB_HOST / DB_NAME / DB_USER / DB_PASSWORD
#   接真实后端时改：
#     SAAS_AGG_GATEWAY_URL    Go 网关（网关状态 / 订单 / AI / 分析 / 合规）
#     SAAS_AGG_NODE_API_URL   Node.js BFF（商品 / 库存）
#   只想看界面效果不想接后端：后台勾选 demo 模式即可，无需改动此处

# 2) 启动开发服务器（必须在 WSL 内，原因见下方「关键说明」）
bash scripts/serve-wsl.sh start
bash scripts/serve-wsl.sh status

# 3) 首次安装：浏览器打开
#    http://127.0.0.1:8090/wp-admin/install.php

# 4) 初始化站点（激活插件 / 切子主题 / 固定链接 / 演示页）
php scripts/wp-bootstrap.php --demo-pages

# 5) 验收
php scripts/verify-site.php
```

常用命令：

```bash
bash scripts/serve-wsl.sh start | stop | restart | status | log
```

### ⚠️ 关键说明：为什么开发服务器必须跑在 WSL 内

MySQL 跑在 WSL 的 Docker 里。如果 PHP 在 Windows 侧运行，**每一次数据库连接都要穿过 Windows ↔ WSL 的 localhostRelay 端口转发**，而这个通道在高频短连接下会**成簇丢包**，表现为：

```
mysqli_real_connect(): Error while reading greeting packet
(HY000/2006): MySQL server has gone away
```

实测数据：Windows 侧跑 PHP 时 **12 次请求失败 7 次**；把 PHP 移进 WSL（与 MySQL 同处一个网络命名空间）后 **15/15 全部成功**。

这不是 WordPress 或代码的问题，是 WSL2 网络栈的已知特性。生产环境不存在这个问题（都在 Linux 里）。

# 第二部分 · 与原生生态的兼容与升级方案

## 2.1 兼容性的四层保证

| 层 | 保证内容 | 怎么被破坏 | 本项目如何规避 |
|---|---|---|---|
| **核心** | 一个字节不改 | 直接编辑核心文件 | 部署层隔离：容器里核心只读；校验层卡口：`verify-core.php` |
| **父主题** | 一个字节不改 | 改父主题文件 | 所有定制在子主题，父主题可独立升级 |
| **官方插件** | 不改动 | 改 `akismet/` 等目录 | 零改动 |
| **数据表** | 用官方规范 | 硬编码前缀/字符集 | `$wpdb->prefix` + `get_charset_collate()` + `dbDelta()` |

## 2.2 WordPress 核心升级

### 为什么核心升级是安全的

因为**核心里没有我们的代码**。升级只是替换官方文件，自研功能全在 `wp-content` 下，不受影响。

### 容器环境的升级步骤

```bash
# 1) 查新版本与 SHA256
curl -s "https://api.wordpress.org/core/version-check/1.7/"

# 2) 更新 Dockerfile 里的版本与 SHA256
vi docker/php/Dockerfile
#    ARG WORDPRESS_VERSION=<新版本>
#    ARG WORDPRESS_SHA256=<对应 SHA256>

# 3) 重建并强制同步核心
WP_FORCE_SYNC_CORE=1 docker compose up -d --build php

# 4) 用新版本重建校验基线
bash scripts/fetch-baseline.sh <新版本> zh_CN

# 5) 验收核心完整性 + 功能
# [已移除] 原 Docker 容器验证脚本 container-verify.sh 已随去 Docker 化删除；请以原生方式（直接运行 PHP/插件校验）替代
```

### 核心升级的回滚

```bash
# 回滚就是把版本号改回去、重建、重启
vi docker/php/Dockerfile      # 改回旧版本号与 SHA256
WP_FORCE_SYNC_CORE=1 docker compose up -d --build php
bash scripts/fetch-baseline.sh <旧版本> zh_CN
# [已移除] 原 Docker 容器验证脚本 container-verify.sh 已随去 Docker 化删除；请以原生方式（直接运行 PHP/插件校验）替代
```

**关键点**：数据库里如果有新版写入的数据结构，回滚核心**不会**自动回退数据库。所以：
- 小版本升级（7.0.4 → 7.0.5）：安全，通常不改数据库结构
- 大版本升级（7.0 → 8.0）：**必须先备份数据库**，回滚时连同数据库一起恢复

`WP_AUTO_UPDATE_CORE=minor` 这个设置就是为此——只允许自动更新安全补丁和小版本，大版本由人工决策。

## 2.3 主题升级

```
父主题 slstyle 升级
    ↓
子主题 slstyle-child 不受影响（独立目录）
    ↓
唯一需要检查的：父主题是否改了子主题依赖的函数名 / 钩子节点
```

**检查方法**：升级父主题后跑一次 `scripts/verify-site.php`，其中"子主题无错误""父主题正确""子主题提供了页面模板"三项会立刻暴露问题。

**回滚**：后台「外观 → 主题」切回即可，或用脚本：

```bash
# [已移除] 原 Docker 升级回滚测试脚本 upgrade-rollback-test.sh 已随去 Docker 化删除    # B 组会在父/子主题之间来回切换做验证
```

## 2.4 插件升级

自定义表用 `dbDelta()` 管理，版本号存在 option 里：

```
新版本代码（SCHEMA_VERSION 1.0.0 → 1.1.0）
    ↓
下次进入后台时检测版本不一致
    ↓
SAAS_Agg_DB::needs_upgrade() === true
    ↓
dbDelta() 增量加字段（不改已有字段、不删数据）
    ↓
更新 saas_aggregator_db_version = 1.1.0
```

**dbDelta 的注意事项**（写新版本时必须遵守，否则升级会失败）：

1. 每个字段必须**独占一行**
2. `CREATE TABLE` 后必须跟两个空格再写字段名
3. 主键定义必须单独一行 `PRIMARY KEY  (id)`
4. 字段间用逗号分隔，且逗号后换行

## 2.5 卸载

后台「插件 → 停用 → 删除」触发 `uninstall.php`：

```php
wp_clear_scheduled_hook( $prune_hook );   // 清定时任务
DROP TABLE wp_saas_agg_logs               // 删审计表
DELETE FROM wp_options WHERE ...          // 清设置项
```

**停用不删数据，删除才删。** 这样停用排查问题后重新启用，历史数据完好无损。

## 2.6 已知的环境限制

| 限制 | 影响 | 规避方式 |
|---|---|---|
| Docker 镜像未装 `imagick` | 缩略图处理用 GD 兜底，画质略低 | 有需要时在 Dockerfile 加回（注释里写了方法）；需能访问 github.com |
| 本地开发服务器不能跑在 Windows 侧 | 跨系统数据库连接成簇丢包 | 一律用 `scripts/serve-wsl.sh` |
| 容器未配置 SMTP | 邮件发不出去 | 装 WP Mail SMTP 之类的插件并配置（见待确认项 #10） |
| Redis 容器起来了但没启用对象缓存 | Transients 走数据库 | 装 Redis Object Cache 插件（见待确认项 #9） |

### 3.1b 真实数据源联通校验

功能校验只证明"链路通"，不证明"数据真"。这一节验证插件确实能从真实微服务取到业务数据。

**各数据源的服务归属（实测结论，不是猜的）：**

| 数据源 | 服务 | 端口 | 路径 |
|---|---|---|---|
| `gateway_status` | gateway-go | 8080 | `/api/gateway/status` |
| `business_core` | gateway-go | 8080 | `/api/orders` |
| `ai_insights` | ai-python | 8000 | `/api/ai/rag`（POST） |
| `analytics` | ai-python | 8000 | `/api/analytics/dashboard` |
| `compliance` | ai-python | 8000 | `/api/compliance/status` |
| `ecommerce` | **node-api** | **3001** | `/api/products` ← 不在网关上 |

**校验方法**：用插件自身链路调用，而不是另写一套 HTTP 请求——这样测的才是真实生效的代码路径。

```bash
# 宿主机本地（WordPress 与微服务同机）
php scripts/verify-upstream.php

# 容器内（微服务跑在宿主机上）
```

**判定标准**：6 个源全部 `status=ok`，且 `items[0]['title']` 是真实业务值（不是 `实时指标` 之类的 demo 文案）。

## 3.2 核心文件未被改动校验

```bash
php scripts/verify-core.php            # 人类可读输出
php scripts/verify-core.php --json     # 机器可读
php scripts/verify-core.php --strict   # 严格模式（wp-content 有变更也报错）
```

**原理**：以 wordpress.org 官方 checksums API 为黄金基线，逐文件比对 MD5。

```
基线来源：https://api.wordpress.org/core/checksums/1.0/?version=7.0.4&locale=zh_CN
基线条目：4171
```

**当前结果：**

```
判定 PASS
基线校验和条目   : 4171
扫描文件数       : 4244
核心改动         : 0
核心缺失         : 0
核心非法新增     : 0
```

**关于 4244 − 4171 = 73 个差值**：全部位于 `wp-content/` 下，是自研主题、自研插件、上传目录与语言包。这是**内容域**，WordPress 设计上就允许用户在这里增删文件，不计入核心改动。想严格区分可以加 `--scope=core` 只扫核心。

**升级后重建基线**：

```bash
bash scripts/fetch-baseline.sh 7.0.5 zh_CN
```

> `fetch-baseline.sh` 内置了条目数校验（少于 100 条视为异常并放弃写入），避免网络异常时写入一个空基线，导致后续校验"假通过"。

## 3.3 升级与回滚测试

分三组：

### A 组 · 插件回滚（停用 → 重新激活）

| 验证点 | 期望 |
|---|---|
| 停用后审计数据仍在 | 条数与停用前一致 |

| 验证点 | 期望 |

**已做的性能设计：**

1. **DDL 不在前台执行**——表结构升级检查只在后台且版本不一致时触发
2. **脚本按模板条件加载**——`dashboard.js` 只在看板页加载，其他页面不背这个请求
3. **聚合结果走 Transients**——避免每次请求都打外部网关
4. **静态资源长缓存**——nginx 侧 `expires 30d` + `immutable`

**生产建议补充：**

- 启用 Redis 对象缓存（容器已备好 `wp004-redis`，装官方插件即可）
- 上 CDN 承载静态资源
