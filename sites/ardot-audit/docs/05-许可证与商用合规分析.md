## 结论（先给判断）

> # 有条件商用

**拆开说是三句话：**

| 使用形态 | 判断 | 说明 |
|---|---|---|
| ① 自建站点对外提供商业服务（SaaS / 企业官网 / 电商） | ✅ **可以，且无附加义务** | GPLv2 不限制"运行"，不分发即不触发源码开放 |
| ② 把自研主题 / 插件打包出售或交付给客户 | ✅ **可以，但必须完整履行 GPLv2 义务** | 见第 2 节 |
| ③ 把 Redis 作为托管服务对外售卖、或 Akismet 用免费 Key 跑商业站 | ❌ **不可以** | 见第 5 节风险 ①② |

**有条件**这三个字，落在两处**当前尚未触发、但一旦启用即违规**的合规负债上：
Redis 7.4 的非开源许可、Akismet 的服务条款。两者目前都是**未启用**状态，所以现状风险为 0。

### 得出该结论的核心依据

1. **WordPress 核心 7.0.4 经官方 checksums 基线比对为零改动**——本次复核结果：改动 0 / 缺失 0 / 非法新增 0，
   意味着核心内所有 GPL 版权与许可声明**完整保留**，不存在"删掉许可头后商用"这类最常见的致命伤。
2. 仓库内**无任何加密/混淆代码**：全量扫描 `ionCube` / `eval(base64_decode)` / `gzinflate(base64_decode)` /
   `str_rot13` 及 300+ 长度 base64 串，命中数为 0。这是 GPL 合规的前置条件（中文商业主题常见违规点）。
3. 自研的 `saas-aggregator` 插件与 `slstyle` / `slstyle-child` 主题**均已主动声明 `GPL-2.0-or-later`**，
   与 WordPress 生态保持一致，不存在许可证冲突。
4. 实际只激活了一个插件——自研的 `saas-aggregator`；Akismet 未激活且无 API Key。
5. 中间件版本均为实测：MySQL 8.0.46 / nginx 1.27.5 / PHP 8.2.33 / Valkey 8.1.9。
   （原 Redis 7.4.11 已于 2026-08-29 替换为 Valkey，见第 5.1 节与 06 文档第 4 节。）

## 2. 商用时需履行的义务

### 2.1 先分清两个场景——这一步决定了 90% 的义务

GPLv2 第 0 节明确写着：**"the act of running the Program is not restricted"**（运行程序的行为不受限制）。

| 场景 | 是否触发 GPL 义务 | 说明 |
|---|---|---|
| **A. 自建站点对外提供商业服务**（本项目当前形态） | ❌ **不触发** | 没有"分发"动作。GPLv2 没有 AGPL 那样的网络使用条款，所以 SaaS 模式无需开源。**这就是常说的 ASP 例外。** |
| **B. 打包出售 / 交付给客户 / 公开发布**主题或插件 | ✅ **完整触发** | 见下 |

> ⚠️ 注意：**给客户部署站点**属于灰色地带。若客户拿到的是服务器访问权（代码留在你的服务器），通常不算分发；
> 若交付的是可复制的代码包（zip、镜像、Git 仓库），则**构成分发**，义务全部触发。

### 2.2 场景 B 下必须履行的义务

1. **随附完整许可证全文**——必须包含 GPLv2 的完整文本，不能只给一个链接或一句"GPL 授权"。
2. **保留所有版权与许可声明**——不得删除原作者的版权头、许可头、NOTICE。
3. **提供完整可构建的源码**——与二进制/部署物一并交付，或提供**有效期至少 3 年的书面要约**（GPLv2 §3b）。
4. **标注修改说明**——修改过的文件必须携带显著声明，说明**修改日期**与**修改人**（GPLv2 §2a）。
5. **整体以 GPLv2+ 授权，不得附加任何限制**——不得追加"禁止商用""禁止二次分发"等条款，
   也不得收取超出复制成本的授权费（GPLv2 §1：可对"传递副本的实际成本"收费，但不得对许可本身收费）。
6. **LGPL 组件（TinyMCE / PHPMailer / Crystal 图标）的额外要求**：
   必须保证使用者能**替换**该库（例如用修改版换回原版），且对库本身的修改需以 LGPL 回馈。

### 2.3 场景 A 下仍需履行的义务

- **不得移除核心的版权与许可声明**（哪怕不分发，删声明会使你的使用失去授权基础）。
  本项目已实测核心零改动，符合要求。
- 若日后分发，需补 2.2 全部内容。

### 2.4 本项目当前差距（场景 B 才需要处理）

| 项 | 现状 | 需补 |
|---|---|---|
| 插件/主题目录内的独立 LICENSE 文件 | ❌ 缺失（仅文件头有声明） | 各补一份 GPLv2 全文 |
| 修改说明标注 | ❌ 自研代码未标修改日期/修改人 | 若对外分发需补 |
| 字体 OFL 文本 | ❌ 仓库未随附 | 分发 twentytwentyfive 时需补 |

## 3. 附加条款、专利授权、商标限制与禁商用声明

### 3.1 专利授权 ⚠️ 这是 GPLv2 的一个真实缺口

- **GPLv2 没有明示的专利授权条款。** 它的处理是间接的（§7：若专利义务与许可义务冲突，则不得分发）。
- **GPLv3 第 11 节才提供明示意图的专利许可**（贡献者授予使用者必要专利，并对专利诉讼设有终止条款）。
- **本项目的有利之处**：WordPress 是 **GPLv2-or-later**，你可以**行使"or later"选项，按 GPLv3 接收它**，
  从而获得明示专利授权。建议在交付文档或 LICENSE 中**明确写明"以 GPLv3 条款接收"**，把这条优势固定下来。
- MySQL 8.0 的 GPLv2 **没有** "or later"，无此选项——但对数据库这类"自用不分发"的组件，专利风险极低。
- 若反向向 WordPress 贡献代码，按 WordPress 的 CLA 政策，贡献者需授予专利许可。

### 3.2 商标限制 ⚠️ 本项目最需要动手处理的一项

**(a) "WordPress" 商标**

- "WordPress"、"WordCamp" 是 **WordPress Foundation** 的注册商标。
- **可以做**：描述性使用，如"本站基于 WordPress 构建""适用于 WordPress 的插件"。
- **不可以做**：用它做产品命名（"WordPress CRM"）、用于域名、用于 Logo、暗示官方背书。
- 本项目命名 `SaaS Aggregator` / `slStyle` 均**未使用 WordPress 字样**，符合商标政策。

**(b) 主题命名与商业品牌 Zibll 的近似风险** ✅ **已于 2026-08-29 整改闭环**

- **原状**：主题原名 **ZibStyle**，描述写着"参考 Zibll 设计风格的原创 WordPress 主题"，代码注释中多处
  出现 `zibll 风格`、`zibll 卡片网格`、`zibll 首页还原` 等表述，与商业中文主题品牌
  **Zibll（子比主题）** 名称近似。
- **已核查的结论：代码确系原创，不存在 Zibll 源码复制。**
  - 全库 grep `zibll` / `_zib_` 前缀函数 / Zibll 版权头，命中的**全部是注释与文案**，无一行是 Zibll 的实现代码。
  - 主题自有函数统一使用 `slstyle_*` 前缀（如 `slstyle_setup`、`slstyle_breadcrumbs`），与 Zibll 的 `_zib_` 前缀体系不同。
  - 因此**不侵犯 Zibll 的代码著作权**。
- **风险性质（独立于开源许可）**：Zibll 是售价数百元的商业主题。以近似名称（ZibStyle）
  命名并明示"参考 Zibll 设计风格"，构成**商标淡化**与**搭便车（不正当竞争）**风险。
  这一条与 GPL 无关，GPL 不授予商标权（GPLv3 §7(e) 亦明确不授予商标许可）。
- **整改结果**：主题已更名为 **slStyle**（目录 `slstyle` / `slstyle-child`，文本域同步为
  `slstyle` / `slstyle-child`），前缀 `ZIBSTYLE_VERSION` → `SLSTYLE_VERSION`；
  全部 "Zibll" 表述已从**线上可见文案**（footer 站点描述、widget 默认文本、关于我们页）
  与代码注释中清除；`hero-zibll.png` → `hero-slstyle.png`，body class `zibll-home` → `slstyle-home`。
  全项目 grep `zibstyle|zibll|子比` **命中 0**。详见 `07-代码通读发现清单.md` 与本文 5.3 节。

### 3.3 禁商用声明

- WordPress 核心及其捆绑的 GPL/LGPL/ISC/BSD 组件中，**不存在任何禁止商业使用的条款**。
- 本项目**唯一**的实质商用限制来自两项**服务/非开源许可**，见第 5 节。

### 3.4 免责与担保

- GPLv2 第 11、12 节明确**不提供任何担保**（"WITHOUT ANY WARRANTY"）。
- 商用部署需自行承担可用性、安全性责任，不能向 WordPress 主张任何质量责任。

### 4.2 一个必须说清的边界

**WordPress 通过 HTTP 调用外部微服务（本项目 6 个数据源），不构成 GPL 上的"衍生作品"。**

- 插件与 `gateway-go` / `ai-python` / `node-api` 之间是 **HTTP 协议通信**，属于 GPLv2 §2 所说的
  **"mere aggregation"（单纯聚合）**——独立程序与插件共存于同一介质/系统，但不构成衍生作品。
- 因此：**下游微服务的许可证不影响本 WordPress 项目的 GPL 合规性**，
  插件也**不需要**因此开源。这一点对商业闭源的后端服务尤其重要。

### 4.3 兼容性小结

**全部依赖与商用兼容。** 唯一的例外曾是 Redis，已于 2026-08-29 换为 BSD-3 的 Valkey（见 5.1）。

**另需注意两处核心自带的文本缺口**（不影响自用，影响分发）：
WP 7.x 新增的 `wp-includes/php-ai-client/third-party/` vendored 了 44 个 MIT 文件
（Nyholm/Psr7、php-http/discovery），但**未随附 MIT 全文**；
`twentytwentyfive` 的 9 个字体族（OFL 1.1）同样**未随附 OFL 文本**。
详见 `docs/06-第三方许可与声明清单.md` 第 5.2 节。

## 5. 潜在法律风险与可行的替代方案

### 5.1 ✅ Redis 非开源许可 —— **已解决（2026-08-29 换为 Valkey）**

> **本节为原始风险分析；处置结果与实测记录见 `docs/06-第三方许可与声明清单.md` 第 4 节。**

**原风险事实**：容器内实测曾为 `Redis server v=7.4.11`。Redis 自 **7.4** 起把许可证从
BSD-3-Clause 改为 **RSALv2 + SSPLv1 双许可**，二者**均未经 OSI 认证、FSF 亦不认为是自由软件**。
compose 里写的是浮动标签 `redis:7-alpine`，会解析到 7.4.x——等于把非开源依赖悄悄带进了交付栈。

**当时的风险边界（供理解为何判定为"当前风险 = 0"）**：

RSALv2 只禁止两件事——

1. 将软件商业化，或**作为托管服务提供给他人**；
2. 移除或隐匿许可、版权声明。

Redis 官方 FAQ 亦明确：*"For end users using Redis for internal or personal usage, there is no change."*
**把 Redis 当作自有站点的内部缓存，不属于 (1)。**

**而且本项目根本没在用 Redis**——三处独立证据：

- `wp-config.php` 中无 Redis 相关配置；
- `public/wp-content/` 下无 `object-cache.php`（Redis 对象缓存 drop-in）；
- 插件与配置代码中 `redis` 关键字命中数为 0。

它是 `docker-compose.yml` 里声明的一个**空转容器**。因此**当前实际风险为 0**，
但属于"将来一启用就引入非开源依赖"的合规负债，且 Redis 官方镜像内未随附任何 LICENSE 文件（已实测全盘搜索无命中），
会给第三方合规审计造成举证困难。

**已选方案（✅ 已执行）**：换 `valkey/valkey:8.1-alpine`。

| 方案 | 说明 | 结论 |
|---|---|---|
| **换 `valkey/valkey:8.1-alpine`** | Linux 基金会项目，**BSD-3-Clause**，从 Redis 7.2.4 fork，RESP 协议兼容，客户端（phpredis）零改动 | ✅ **已采用**，实测 Valkey 8.1.9，PING/读写/phpredis 直连全通过 |
| 降级 `redis:7.2-alpine` | 7.2 是最后一个 BSD-3 版本 | 未采用（分叉项目更可持续） |
| 直接从 compose 删除该服务 | 既然没用到，删掉最干净 | 未采用（保留缓存能力以备后用） |

⚠️ **执行中发现的真坑（值得单独记一笔）**：Valkey 首次启动**反复重启**，日志报
`Can't handle RDB format version 12`。原因是 Valkey 从 Redis 7.2.4 分叉，而 Redis 7.4
引入了 RDB v12 与新的 multi-part AOF 目录结构，**Valkey 8.1 读不了旧格式**。
→ 结论：**Valkey 是协议层 drop-in，不是持久化文件格式层 drop-in**。
有 Redis 7.4 存量数据的环境必须走数据迁移，不能照抄"删卷重建"。

### 5.2 🟡 Akismet 服务条款 —— 免费 Key 不得用于商业站（当前未激活，风险 = 0）

**事实**：Akismet 5.7 随 WordPress 分发，**代码是 GPLv2-or-later**（可自由商用、修改、分发），
但**反垃圾服务是 Automattic 的商业服务**，适用其 ToS。
ToS 第 1 节原文：*"Free keys are for personal, non-commercial sites only."*；第 3 节：
*"For commercial sites, you must obtain an API Key by purchasing one of our paid plans."*

**当前状态（实测）**：插件**未激活**，`wordpress_api_key` 未配置 → **风险 = 0**。

**一旦激活即违规的情形**：在商业站点上启用 Akismet + 使用免费 Personal Key。
后果是 API Key 被停用（错误码 10001/10010），而非法律诉讼——性质上属于**合同违约**，风险可控。

**替代方案：**

| 方案 | 说明 |
|---|---|
| 保持停用 | 当前状态，零成本零风险；建议同时用评论审核、验证码等替代手段 |
| 购买 Plus 计划 | 约 $10/月/站（≤9 站），商业站合规 |
| 换开源反垃圾插件 | 如 Antispam Bee（GPLv2，无外部服务依赖，数据不出站，更利于 GDPR 合规） |

> 💡 顺带一提：若站点面向欧盟用户，Akismet 会把评论数据发送到 Automattic（美国），
> 涉及跨境传输评估。Antispam Bee 本地处理，在这点上更省事。
