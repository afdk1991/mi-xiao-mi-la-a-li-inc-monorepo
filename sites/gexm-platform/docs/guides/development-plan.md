## 接口设计规范

### RESTful API 规范

#### 通用规则

| 规则 | 说明 | 示例 |
|------|------|------|
| URL 版本化 | 使用 `/api/v1/` 前缀 | `/api/v1/users` |
| 资源命名 | 使用复数名词 | `/api/v1/users`、`/api/v1/orders` |
| HTTP 方法 | GET/POST/PUT/DELETE | GET 查询、POST 创建、PUT 更新、DELETE 删除 |
| 响应格式 | JSON，包含 code/message/data | `{"code": 200, "message": "success", "data": {...}}` |
| 错误处理 | 统一错误码，详细错误信息 | `{"code": 400, "message": "参数错误", "data": {...}}` |

#### 分页规范

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| page | number | 1 | 页码 |
| pageSize | number | 10 | 每页条数 |
| sortBy | string | created_at | 排序字段 |
| sortOrder | string | desc | 排序方向（asc/desc） |

#### 响应示例

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "pageSize": 10
  }
}
```

### 微服务间通信规范

#### 服务发现

- 服务注册：Consul
- 服务调用：HTTP/gRPC
- 负载均衡：Consul 内置

#### 通信协议

| 场景 | 协议 | 说明 |
|------|------|------|
| 同步调用 | HTTP/REST | 常规服务间调用 |
| 高性能调用 | gRPC | 需要高性能的场景 |
| 异步通信 | 消息队列 | 事件驱动、解耦 |

#### 错误处理

- 超时重试：3 次，指数退避
- 熔断降级：服务不可用时返回默认值
- 追踪 ID：全链路追踪，贯穿所有服务

## 质量保障计划

### 代码审查流程

```
开发完成 → 提交 PR → 自动化检查（ESLint、TypeScript）→ 代码审查（至少1人）→ 测试验证 → 合并
```

### 测试策略

| 测试类型 | 范围 | 工具 | 覆盖率目标 |
|----------|------|------|-----------|
| 单元测试 | 函数/类/模块 | Jest | ≥ 80% |
| 集成测试 | 服务间调用 | Jest + Supertest | ≥ 60% |
| E2E 测试 | 端到端业务流程 | Playwright | 核心流程 100% |
| 性能测试 | 接口响应时间 | autocannon | P95 < 200ms |
| 安全测试 | 漏洞扫描 | OWASP ZAP | 高危漏洞 0 |

### 质量门禁

- `npm run lint` 零错误
- 测试覆盖率 ≥ 70%
- 性能压测通过
- 代码审查通过

## 总结

本开发计划基于项目迭代方案和路线图，明确了剩余功能模块的优先级排序、智能体任务分配、接口设计规范和时间节点。核心原则是：

1. **渐进式演进**：先完成微服务拆分规划，再逐步实现核心服务拆分
2. **质量优先**：每个模块完成后进行代码审查和测试验证
3. **数据驱动**：基于度量指标决策，避免盲目优化
4. **风险可控**：提前识别风险，制定应对策略

各智能体需严格遵循本计划，按时完成各自负责的模块，并定期进行进度汇报。
