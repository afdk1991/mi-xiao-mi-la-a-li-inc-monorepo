## 执行摘要

### 项目概述

GEXM 是一个全平台电商系统，包含：
- **后端**：Node.js + Express + better-sqlite3 + Socket.io
- **前端**：uni-app（支持 H5、小程序、APP）
- **数据库**：SQLite（WAL 模式）
- **功能模块**：用户认证、商品管理、订单系统、支付、优惠券、会员积分、秒杀、聊天、管理后台

### 总体评价

项目已具备基础安全框架，包括 JWT 认证、CSRF 防护、XSS 过滤、速率限制、参数化查询等。**近期已完成以下安全改进**：
- ✅ 优惠券功能从内存存储迁移到数据库持久化
- ✅ 会员积分功能从内存存储迁移到数据库持久化
- ✅ 签到功能从内存存储迁移到数据库持久化
- ✅ 支付签名从 MD5 升级为 HMAC-SHA256
- ✅ WebSocket 重连逻辑内存泄漏修复
- ✅ XSS 过滤增强（使用 xss 库替代自实现黑名单）
- ✅ 管理员操作审计日志
- ✅ 数据库自动备份机制
- ✅ RBAC 权限管理基础框架
- ✅ 敏感操作二次验证机制

**仍存在中高风险问题**，特别是：
- 默认弱密钥和敏感配置泄露风险
- 支付回调接口缺乏强认证机制
- 管理后台缺乏细粒度权限控制和操作审计

## 1. 数据传输安全

### 1.1 HTTPS 配置

| 项目 | 详情 |
|------|------|
| **风险等级** | 中 |
| **利用难度** | 中 |
| **影响范围** | 生产环境数据传输 |

**风险描述**：
- 开发环境 `FORCE_HTTPS=false`，HTTP 明文传输
- HTTPS 强制跳转依赖 `x-forwarded-proto` 头，需正确配置反向代理
- 生产环境需确保 TLS 证书正确配置和自动续期

**代码位置**：
- `packages/server/src/middleware/security.js:149-154` - forceHttpsMiddleware
- `packages/server/.env.example:11` - FORCE_HTTPS=false

**修复建议**：
1. 生产环境强制启用 HTTPS，配置 HSTS（已配置 CSP 中的 HSTS）
2. 确保反向代理正确设置 `x-forwarded-proto`
3. 配置自动证书续期（如 Let's Encrypt + certbot）
4. 使用 TLS 1.2+，禁用弱密码套件

## 2. 数据存储安全

### 2.1 密码存储

| 项目 | 详情 |
|------|------|
| **风险等级** | 中 |
| **利用难度** | 高 |
| **影响范围** | 用户密码安全 |

**风险描述**：
- 使用 bcryptjs 进行密码哈希，salt rounds = 10
- 哈希强度基本够用，但现代硬件条件下建议增加到 12+
- 密码哈希同步计算（hashSync），高并发下可能阻塞事件循环

**代码位置**：
- `packages/server/src/models/userModel.js:27` - bcrypt.hashSync(userData.password, 10)
- `packages/server/src/models/userModel.js:106` - updatePassword 使用 hashSync
- `packages/server/src/models/index.js:706` - 默认管理员密码哈希

**修复建议**：
1. 将 bcrypt salt rounds 提升到 12-14
2. 考虑使用异步 bcrypt 避免阻塞事件循环
3. 强制用户首次登录修改默认密码
4. 添加密码历史记录，防止重复使用最近 N 个密码

### 2.2 敏感数据加密

| 项目 | 详情 |
|------|------|
| **风险等级** | 高 |
| **利用难度** | 低 |
| **影响范围** | 用户 PII 数据 |

**风险描述**：
- 手机号、地址、邮箱等 PII 数据明文存储在数据库中
- 数据库文件可直接访问，一旦泄露将导致大规模隐私泄露
- 收货地址包含姓名、电话、详细地址等敏感信息，以 JSON 明文存储

**代码位置**：
- `packages/server/src/models/index.js:38-46` - users 表（phone 明文）
- `packages/server/src/models/index.js:241-255` - addresses 表（全明文）
- `packages/server/src/models/orderModel.js:80-82` - shipping_address JSON 明文

**修复建议**：
1. 对手机号、身份证、地址等敏感字段进行加密存储
2. 使用 AES-256-GCM 等认证加密算法
3. 加密密钥与数据库分离存储（如使用 KMS 或环境变量）
4. 数据库文件设置严格的文件系统权限（600）
5. 考虑使用 SQLite 加密扩展（如 SQLCipher）

### 2.3 Token 存储

| 项目 | 详情 |
|------|------|
| **风险等级** | 严重 |
| **利用难度** | 低 |
| **影响范围** | 用户认证安全 |

**风险描述**：
- JWT Secret 使用默认弱密钥 `gexm_jwt_secret_key_2024`，生产环境如未修改可被轻易破解
- Refresh Token 同样使用默认弱密钥
- JWT 未设置 issuer、audience 等声明，降低安全性
- Refresh Token 存储在数据库中但未哈希存储（虽然 JWT 本身不可篡改，但可被直接盗用）

**代码位置**：
- `packages/server/.env:4-7` - 默认弱密钥
- `packages/server/src/config/index.js:8-11` - JWT 配置
- `packages/server/src/models/userModel.js:164-176` - Token 生成
- `packages/server/src/models/userModel.js:178-186` - Refresh Token 存储

**修复建议**：
1. **立即**生成 32 位以上强随机 JWT Secret（使用 `crypto.randomBytes(32).toString('hex')`）
2. 生产环境启动时强制校验密钥强度（已部分实现，需确保生效）
3. JWT 添加 issuer、audience 声明
4. 考虑 Refresh Token 使用随机字符串而非 JWT，并哈希存储
5. 添加 Token 黑名单机制（用于主动登出）

### 4.2 XSS 防护

| 项目 | 详情 |

| **利用难度** | 中 |

- 使用基于黑名单的 XSS 过滤（移除 script、iframe、事件处理等）

- CSP 策略包含 `'unsafe-inline'`，降低了 XSS 防护效果

**修复建议**：
1. 考虑使用成熟的 XSS 过滤库（如 DOMPurify、xss）替代自实现
2. 输出编码比输入过滤更可靠，确保所有用户输入在输出时正确编码
3. 逐步移除 CSP 中的 `'unsafe-inline'`，使用 nonce 或 hash
4. 对富文本内容使用严格的白名单过滤
5. 设置 HttpOnly 和 Secure Cookie 标志

### 4.3 CSRF 防护

| 项目 | 详情 |
|------|------|
| **风险等级** | 高 |
| **利用难度** | 中 |
| **影响范围** | 状态变更操作安全 |

**风险描述**：
- CSRF Token 存储在 Cookie 中，但设置了 `httpOnly: false`，可被 JS 读取（设计如此，但增加了 XSS 利用风险）
- 小程序和 APP 端不支持 Cookie，CSRF 保护对这些端无效
- 管理后台部分 POST/PUT/DELETE 操作有 CSRF 保护，但 GET 接口未做敏感操作检查
- 支付回调接口无 CSRF 保护（设计如此，但需其他认证机制）

**代码位置**：
- `packages/server/src/middleware/security.js:77-91` - csrfTokenMiddleware（httpOnly: false）
- `packages/server/src/middleware/security.js:93-133` - csrfProtectionMiddleware
- `packages/server/src/middleware/csrfConfig.js` - CSRF 路由配置
- `packages/app/src/utils/request.js:12-28` - 前端 CSRF Token 获取

**修复建议**：
1. 对于不支持 Cookie 的客户端（小程序、APP），考虑使用其他 CSRF 防护方式（如请求头校验、Token 绑定）
