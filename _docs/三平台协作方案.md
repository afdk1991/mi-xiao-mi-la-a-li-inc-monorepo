# 三平台协作方案：GitHub · GitHub Packages · EdgeOne Makers

> 本方案定义「代码托管 → 包管理 → 边缘应用发布」的整体协作架构，明确三者职责边界、相互集成方式与端到端流程。
> 落地代码位于本仓库 `.github/workflows/` 与根 `.npmrc`、各 `shared/*` 包的 `package.json` / `tsconfig.build.json`。

---

## 1. 三者职责边界

| 平台 | 角色定位 | 负责什么 | 不负责什么 |
|---|---|---|---|
| **GitHub** | 代码源真相 + CI/CD 编排 | 源码托管（私有仓 `afdk1991/mi-xiao-mi-la-a-li-inc-monorepo`，默认 `master`）、PR 评审、Actions 流水线、打标签触发发布 | 不提供运行态；不做 npm 包分发之外的存储 |
| **GitHub Packages** | 私有 npm 注册表（仅共享库） | 存放 `@afdk1991/shared-{map,http,config}` 三个共享库，版本不可变、按 scope 鉴权 | 不托管应用、不构建边缘产物 |
| **EdgeOne Makers / Pages** | 边缘应用发布与运行目标 | 接收构建产物并分发到边缘节点（`edgeone pages deploy` / `edgeone makers deploy`），提供预览与生产环境 | 不托管源码、不管理包版本 |

**关键决策**：GitHub Packages **只放 3 个共享库**，不放应用。应用是「源码在 GitHub、产物在 EdgeOne」，二者通过「构建时拉取共享包」这一唯一集成点耦合，避免把整个 monorepo 当成 npm 包发布。

## 2. 集成架构

```
                ┌──────────────────────────────────────────────────────┐
   git push ──▶ │  GitHub (master / PR)                                │
                │   ├─ shared/** 变更 ─▶ publish-packages.yml           │
                │   ├─ apps/** 变更  ─▶ deploy-edgeone-app.yml          │
                │   └─ sites/** 变更 ─▶ deploy-edgeone-site.yml         │
                └───────────────┬───────────────────┬──────────────────┘
                                │                   │
                 ① 发布共享包    │                   │ ② 拉取共享包 + 构建
                                ▼                   ▼
                ┌───────────────────────┐   ┌──────────────────────────┐
                │ GitHub Packages        │   │ EdgeOne 构建步骤          │
                │ @afdk1991/shared-*     │◀──│ npm install 时经 .npmrc   │
                │ (GITHUB_TOKEN 写入)    │   │ 鉴权拉取私有包            │
                └───────────────────────┘   └───────────┬──────────────┘
                                                        │ ③ 部署产物
                                                        ▼
                                          ┌──────────────────────────┐
                                          │ EdgeOne Makers / Pages     │
                                          │ 边缘节点（production/preview）│
                                          └──────────────────────────┘

   总开关：release.yml（打 v* 标签）→ ① 发布三个共享包 → ② 触发两个 EdgeOne 部署
```

**两条鉴权令牌串起三平台**：
- `GITHUB_TOKEN`（内置，无需自建）：publish 写包、deploy 读包（经 `NODE_AUTH_TOKEN` 注入 `.npmrc`）。
- `EDGEONE_API_TOKEN`（仓库 Secret）：EdgeOne 部署鉴权。

---

## 3. 鉴权与凭据矩阵

| 凭据 | 来源 | 用途 | 作用域 | 落库 |
|---|---|---|---|---|
| `GITHUB_TOKEN` | Actions 运行时内置 | 发布/读取 GitHub Packages | `packages: write`(发布) / `packages: read`(消费) | 不落库（运行时注入） |
| `NODE_AUTH_TOKEN` | 部署流中 `echo … >> $GITHUB_ENV` | 让 npm 用上述令牌访问 Packages | 仅 `@afdk1991` scope（根 `.npmrc` 限定） | 不落库 |
| `EDGEONE_API_TOKEN` | 仓库 Secret（`EDGEONE_PAGES_API_TOKEN` 在 email-aggregator 分支） | `edgeone pages/makers deploy` 鉴权 | EdgeOne 项目 | 仅 Secrets，不入库 |
| PAT | 无需 | —— | —— | 不推荐 |

> 根 `.npmrc` 只写 `//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}`，令牌值从环境变量读取，明文绝不入库。

## 4. 端到端协作流程

### 场景 A：共享库变更（GitHub → Packages）
1. 修改 `shared/{map,http,config}/src/**`。
2. 推到 `master`（命中 `shared/**` 路径）→ `publish-packages.yml` 触发。
3. 对每个包：`npm install` → `tsc -p tsconfig.build.json` 产出 `dist/` → `npm publish` 到 Packages。
4. 幂等：版本已存在则跳过，可安全重跑。

### 场景 B：应用上线（GitHub → 拉包 → EdgeOne）
1. 修改 `apps/delivery-router/**` 推到 `master` → `deploy-edgeone-app.yml` 触发。
2. 工作流先导出 `NODE_AUTH_TOKEN=$GITHUB_TOKEN`，`npm ci` 时可透明拉取 `@afdk1991/shared-*`（若应用已接入）。
3. `npm run build` 产出 `dist/` → `edgeone pages deploy dist` 部署。
4. PR 走 `preview` 环境，master 走 `production` 环境。

### 场景 C：协调发布（三者总开关）
1. 打标签 `git tag v1.2.0 && git push origin v1.2.0` → `release.yml` 触发。
2. `publish-packages` _job 发布三个共享包到 Packages。
3. `deploy-edge` job（`needs: publish-packages`）用 `gh workflow run` 依次触发
   `deploy-edgeone-app.yml` 与 `deploy-edgeone-site.yml`，确保「先出新包、再出新站」。

## 6. 在应用中消费共享包

根 `.npmrc` 已配置 scope 鉴权，应用只需：

```jsonc
// apps/delivery-router/package.json
{
  "dependencies": {
    "@afdk1991/shared-map": "^1.0.0",
    "@afdk1991/shared-http": "^1.0.0",
    "@afdk1991/shared-config": "^1.0.0"
  }
}
```

```ts
import { createProvider, buildMapSettings } from '@afdk1991/shared-map'
import { http } from '@afdk1991/shared-http'
```

CI 构建步骤会在 `npm install` 前注入 `NODE_AUTH_TOKEN`，无需本地配置即可拉取私有包。
> 当前各应用尚未强制接入（多数无 `node_modules`），新代码可直接 import，存量实现按需替换。

## 7. 关键技术决策与坑

| 项 | 决策 / 坑 | 处置 |
|---|---|---|
| 共享包可消费性 | 旧 `package.json` 的 `main` 指向 `src/index.ts`、`build` 是 `tsc --noEmit`，发布包无 JS | 改为指向 `dist/`、`tsconfig.build.json` 真正 emit JS + `.d.ts`、`files: ["dist"]` |
| `.edgeone/` 部署源 | CLI 把它当构建标记目录，部署后根为空 → 首页 404 | 用普通目录名（`_deploy` / `_edgeone_publish`），已在脚本固化 |
| 部署目录含 `package.json` | CLI 自动跑 `pnpm install`，本机无 pnpm 即失败 | 部署前 `rm -f …/package.json`（白名单复制） |
| EdgeOne CLI 版本漂移 | `@latest` 让 `deploy --json` 输出结构变化、今天能发明天发不出 | 固定版本（如 `1.6.40`） |
| Packages 令牌 | 自建 PAT 易被撤销 | 全程用内置 `GITHUB_TOKEN`，发布/消费同令牌 |
| 单文件体积 | GitHub 限 100MB/文件 | 推送前 `filter-branch` 剔除 `_backups/` 大 pack |
