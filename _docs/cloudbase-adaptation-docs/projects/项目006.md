# 项目006 · CloudBase 适配方案

> 适配等级：**C · 中等（可部分上云）** ｜ 预估工作量：**2–3 天（仅接口层）** ｜ 代码改动：**中等**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | WordPress 插件 myp-core（PHP 81 处）+ MySQL（15 处）+ 支付（5 处） |
| 源文件规模 | 85 个源文件 |
| 当前数据层 | MySQL 15 处（ReportService.php、CartModel.php 等自研 Model 层） |
| 认证方式 | WordPress 原生 |
| 文件/存储 | 未见独立文件存储 |
| 后端形态 | myp-core 插件 + REST API（PaymentApi.php） |
| 已接入云服务 | **无** CloudBase 接入 |

与项目004 不同，这个项目的 PHP 是**自研插件 myp-core**，且有清晰的 Model 层
（CartModel.php、ReportService.php）—— 说明数据访问是**经过封装的**，不是散落的裸 SQL。

这个区别很关键：**有 Model 层 = 可以换数据层实现**。
若确实要上云，改造面比项目004 小得多。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| 自研 Model 层（CartModel.php 等） | 可适配 CloudBase（需重写 Model 实现） | Model 层存在意味着改造有统一入口 |
| PaymentApi.php 支付接口 | 云函数（保留支付 SDK） | 接口可上云，支付链路逻辑不变 |
| ReportService.php 报表 | 云数据库聚合查询 | 报表类查询迁云需重写聚合逻辑 |
| MySQL | CloudBase MySQL | 同为关系型，SQL 可复用 |

## 3. 接入点（需要改动的具体位置）

1. `myp-core/src/Database/CartModel.php —— Model 层，改造主入口`
2. `myp-core/src/Core/ReportService.php —— 报表服务，聚合查询需重写`
3. `myp-core/src/Api/PaymentApi.php —— 支付接口，上云需谨慎`
4. `myp-core/src/Core/Bootstrap.php —— 启动引导，SDK 初始化位置`
5. `myp-core/src/Admin/AdminPageBase.php —— 后台页面基类`

## 4. 改造步骤

### 步骤 1：先评估：真的需要上云吗

作为 WordPress 插件，它依赖 WP 的生命周期与钩子。
**脱离 WordPress 上云意味着它不再是插件** —— 这是架构级决策，不是技术细节。

### 步骤 2：若上云：从 Model 层切入

CartModel 等 Model 类改为 CloudBase 数据访问实现，上层 Service 保持不变。
这是有 Model 层项目最省力的改法。

### 步骤 3：报表类查询单独评估

ReportService 的聚合查询在文档型数据库里需要重写为聚合管道。
若保留 CloudBase MySQL，则 SQL 可直接复用 —— **推荐保留关系型**。

## 5. 风险与注意

- 插件形态与云函数形态冲突：作为 WP 插件运行时依赖 WP 环境，上云后需独立运行。
- 支付接口（PaymentApi.php）上云涉及资金链路，改造风险高，建议最后做或不做。
- 若选文档型数据库，报表聚合查询需全部重写为聚合管道，工作量翻倍 —— 选 MySQL 更稳。
