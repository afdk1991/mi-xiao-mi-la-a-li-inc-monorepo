# 项目005机箱 · CloudBase 适配方案

> 适配等级：**B- · 可迁但需先瘦身** ｜ 预估工作量：**1 天（先瘦身）** ｜ 代码改动：**小（工具脚本）**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | Python 脚本；**pylibs/ 打包了 PIL / reportlab 等重型依赖（485 个源文件绝大部分是它）** |
| 源文件规模 | 485 个源文件（其中 pylibs/ 占绝大多数） |
| 当前数据层 | Redis 89 处（多为 pylibs 内部误命中）；Flask/Django 3 处（同样是 reportlab 误命中） |
| 认证方式 | 无 |
| 文件/存储 | 本地文件输出 |
| 后端形态 | **纯本地脚本**，无服务端 |
| 已接入云服务 | **无** |

这个项目的扫描结果需要**谨慎解读**：485 个源文件里绝大多数是 `pylibs/` 下打入的
PIL、reportlab 等第三方库源码。所谓"Redis 89 处""Flask 3 处"基本是**库内部代码的误命中**，
不是业务依赖。

真实业务代码规模远小于扫描数字。**不要基于这个扫描结果做迁移决策**。
实际形态是：一个用 Python 生成机箱相关文档/图片的本地工具。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| 本地 Python 脚本 | CloudBase 云函数（Python 运行时） | 若需要 Web 化/定时生成，可上云函数 |
| PIL / reportlab（重型依赖） | 云函数层（Layer） | 依赖体积大，**必须打包成层**，否则冷启动极慢 |
| 本地文件输出 | 云存储 | 生成物上传云存储，返回可访问 URL |

## 3. 接入点（需要改动的具体位置）

1. `pylibs/ —— 第三方库打包目录，改造时排除；评估用 requirements.txt 替代`
2. `项目根目录的实际业务 .py 脚本 —— 真正的改造对象`

## 4. 改造步骤

### 步骤 1：先瘦身：剥离 pylibs

用 requirements.txt + 虚拟环境替代把库源码打进项目。
**这一步是任何上云动作的前提** —— 带着 pylibs 上云，部署包会大到无法接受。

### 步骤 2：评估是否真的需要上云

如果它只是你本机偶尔跑一次的工具，**不上云是正确的选择**。
只有当你需要"别人也能用"或"定时自动生成"时，云函数才有价值。

### 步骤 3：若上云：依赖打包为层

PIL/reportlab 体积大，做成云函数层复用，避免每次部署都上传依赖。

## 5. 风险与注意

- **扫描数字严重失真**（485 文件 / Redis 89 处均为 pylibs 误命中），据此估工时会严重高估。
- pylibs 的存在会让部署包体积爆炸，上云前必须剥离。
- 若没有 Web 化需求，上云是过度设计 —— 本地工具保持本地即可。
