# 项目009商品采集 · CloudBase 适配方案

> 适配等级：**A · 原生受益** ｜ 预估工作量：**2–3 天** ｜ 代码改动：**中等**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | EdgeOne Pages + edge-functions（28 处地图/13 处 REST）+ IndexedDB 本地存储 |
| 源文件规模 | 59 个源文件 |
| 当前数据层 | **IndexedDB 5 处**（src/backup.ts、TrajectoryPanel.tsx）—— 数据全在本地 |
| 认证方式 | 未见独立认证（package-lock.json 有 1 处信号） |
| 文件/存储 | IndexedDB 做备份 —— 数据易失 |
| 后端形态 | edge-functions/api/{falcon,map,sync}.js —— EdgeOne 边缘函数 |
| 已接入云服务 | **无** CloudBase；走 EdgeOne Pages |

数据全部存在浏览器 IndexedDB 里 —— **这是最危险的架构**：清缓存/换设备/换浏览器数据全丢，
且无法多端协同。src/backup.ts 说明你已经意识到这个问题并做了备份机制，但本地备份救不了设备丢失。

采集类业务的商品数据、轨迹数据本就该在云端。这是 CloudBase 价值最明确的项目之一。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| IndexedDB（5 处） | 云数据库集合 | **核心改造**：本地 → 云端，可保留 IndexedDB 做离线缓存 |
| src/backup.ts 备份逻辑 | 云数据库自动持久化 | 上云后本地备份机制可简化为离线缓存 |
| edge-functions/api/*.js | CloudBase 云函数 | 边缘函数迁云函数；若依赖 EdgeOne Pages 部署可保留前端 |
| src/amap.ts 地图调用 | 云函数代理 | Key 收敛（edge-functions/api/map.js 已做代理，思路正确） |
| localStorage（9 处） | 云存储/云数据库 | 配置类留本地，业务数据上云 |

## 3. 接入点（需要改动的具体位置）

1. `src/backup.ts —— 本地备份逻辑，上云后改造为离线缓存层`
2. `src/components/TrajectoryPanel.tsx —— 轨迹数据读写，IndexedDB 主要使用点`
3. `edge-functions/api/falcon.js、map.js、sync.js —— 边缘函数，迁云函数候选`
4. `src/amap.ts —— 地图 Key 与调用封装`

## 4. 改造步骤

### 步骤 1：设计数据模型（先做）

商品采集数据、轨迹数据分别建集合。轨迹数据量可能较大，
建议按时间分片存储，并在 `createdAt` 上建索引。

### 步骤 2：IndexedDB → 云数据库（核心）

保留 IndexedDB 作为**离线缓存**，云端为准。写入走"先本地后同步"或"直接云端+本地缓存"，
**不要设计双向同步** —— 双向同步的冲突处理会吃掉大量工期。

### 步骤 3：边缘函数迁云函数

falcon.js / map.js / sync.js 评估：若只是代理转发，迁 CloudBase 云函数无成本；
若依赖 EdgeOne 特有 API（如边缘 KV），需重写。

### 步骤 4：分页与索引

采集数据会持续增长，查询必须加分页（orderBy + skip + limit）与索引，否则后期会明显变慢。

## 5. 风险与注意

- **IndexedDB 数据丢失风险是当前最紧迫的问题**，优先于一切新功能。
- 轨迹数据量若很大，需评估云数据库存储成本与查询性能，必要时按时间归档。
- 不要做双向同步 —— 单向"云端为准 + 本地缓存"能省掉 80% 的冲突处理工作。
- edge-functions 若用了 EdgeOne 专有能力，迁移成本会高于预期，需先核实。
