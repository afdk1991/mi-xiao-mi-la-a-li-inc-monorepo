# 代驾距离收费计算 · CloudBase 适配方案

> 适配等级：**A · 原生受益（结构最近）** ｜ 预估工作量：**1–2 天** ｜ 代码改动：**小**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | 微信小程序 + 云函数（amap-proxy）+ 高德地图 |
| 源文件规模 | 15 个源文件 |
| 当前数据层 | 无数据库；localStorage 3 处（deploy/index.html、index.html） |
| 认证方式 | 无 |
| 文件/存储 | 无独立文件存储 |
| 后端形态 | **已有云函数**：cloud-functions/amap-proxy.js、cloudfunctions/amap-proxy/index.js |
| 已接入云服务 | **已有云函数架构**（EdgeOne 云函数），但非 CloudBase |

这是**离 CloudBase 最近的一个项目** —— 它已经在用云函数代理高德地图 API（amap-proxy），
架构思路与 CloudBase 云函数**完全一致**。工作量很小：把云函数宿主从 EdgeOne 换到 CloudBase，
再把 localStorage 里的计算结果/历史记录迁到云数据库。

注意：项目同时存在 `cloud-functions/` 和 `cloudfunctions/` 两个目录，需先确认哪个是当前在用版本。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| amap-proxy 云函数 | CloudBase 云函数（原样迁移） | **代码几乎不用改**，换 SDK 初始化与部署目标即可 |
| 高德 Key（云函数内） | 云函数环境变量 | 保持服务端代理，Key 不落前端 —— 这个设计是对的，别改 |
| localStorage 历史记录（3 处） | 云数据库集合 | 换设备不丢，可做历史账单 |
| 计费规则 | 云数据库配置集合 | **规则外置**后无需重新发版即可调价 |

## 3. 接入点（需要改动的具体位置）

1. `cloud-functions/amap-proxy.js 与 cloudfunctions/amap-proxy/index.js —— 先确认哪个在用（两个目录并存）`
2. `index.html、deploy/index.html —— localStorage 读写点`
3. `.edgeone/cloud-functions/api-node —— EdgeOne 部署产物，迁移时需评估是否保留`
4. `.edgeone/assets/cloudfunctions —— 同上`

## 4. 改造步骤

### 步骤 1：确认在用云函数版本

cloud-functions/ 与 cloudfunctions/ 两个目录并存，**先确认哪个是当前部署版本**，避免改错地方。

### 步骤 2：迁移云函数到 CloudBase

amap-proxy 逻辑原样保留，只改：SDK 初始化、部署目标、Key 走环境变量。
这是本次 16 个项目里**改动最小、见效最快**的一次迁移。

### 步骤 3：计费规则外置

把计费单价/阶梯规则放进云数据库配置集合，App 启动时拉取。
现在改价要改代码重新发版，外置后改配置即可 —— **这是本项目最大的业务价值点**。

### 步骤 4：历史记录上云

3 处 localStorage 迁云数据库，加微信登录即可跨设备查看历史账单。

## 5. 风险与注意

- 两个云函数目录并存（cloud-functions/ 与 cloudfunctions/），改错目录会导致线上不生效。
- 高德 Key 当前是 Web 服务 API 类型（你此前确认过），迁云函数后仍走服务端调用，类型无需变更。
- 计费规则外置后要设计默认值兜底 —— 云数据库连接失败时不能让 App 无法计价。
