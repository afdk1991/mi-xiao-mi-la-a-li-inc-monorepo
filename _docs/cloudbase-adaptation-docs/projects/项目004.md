# 项目004 · CloudBase 适配方案

> 适配等级：**C · 重资产（不建议迁移）** ｜ 预估工作量：**不建议迁移** ｜ 代码改动：**大（不划算）**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | WordPress + zibstyle 主题（PHP 155 处）+ MySQL（8 处） |
| 源文件规模 | 240 个源文件（含 backups/ 与 public/ 完整 WP 安装） |
| 当前数据层 | MySQL 8 处（saas-aggregator/includes/class-db.php 等） |
| 认证方式 | WordPress 原生认证 |
| 文件/存储 | 文件上传 1 处（akismet 插件） |
| 后端形态 | WordPress + PHP（public/ 下是完整 WP 核心） |
| 已接入云服务 | **无** CloudBase 接入 |

这是完整的 WordPress 站点（public/ 下是 WP 核心文件，含 wp-admin/wp-content），
配 zibstyle 主题。PHP 155 处、MySQL 8 处都是典型 WP 结构。

**核心判断：WordPress 迁 CloudBase 不划算。** WordPress 的数据模型深度绑定 MySQL
（wp_posts / wp_postmeta / wp_options 及上千个插件表结构），迁到文档型数据库等于重写 WordPress。

CloudBase 已支持 MySQL，理论上可换数据库连接，但收益极低 ——
你只是把数据库搬了个家，还要承担连接延迟与迁移风险。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| WordPress MySQL | CloudBase MySQL（理论可行，不建议） | 可换连接串，但收益低、风险高 |
| WP 媒体库 | 云存储 | 可选：媒体文件迁云存储能省服务器带宽，但需插件改造 |
| backups/ 多份主题备份 | **不需要云化** | 本地备份或 Git 即可 |
| saas-aggregator（PHP 自研） | 可选：迁云函数 | 若这部分是独立聚合服务，可单独上云 |

## 3. 接入点（需要改动的具体位置）

1. `public/ —— 完整 WordPress 核心，**不建议改动**`
2. `backups/2026-08-29-theme-rename/zibstyle/、backups/2026-08-30-fixes/ —— 备份目录，改造排除`
3. `backups/2026-08-30-fixes/saas-aggregator/includes/class-db.php —— 自研数据层，唯一可选接入点`
4. `_dist/checksums-*.json —— 校验文件，非源码`

## 4. 改造步骤

### 步骤 1：不要动 WordPress 核心

public/ 下是完整 WP 安装，任何数据层改动都会波及插件兼容性。

### 步骤 2：若只想省带宽：媒体库迁云存储

这是 WordPress 唯一值得做的 CloudBase 动作 —— 媒体文件走云存储 CDN，
能省服务器带宽。需要插件或代码层改造，属于可选优化。

### 步骤 3：saas-aggregator 可独立评估

这个自研 PHP 聚合服务（class-db.php / class-rest.php）与 WP 耦合度较低，
若需要独立部署，可单独迁云函数。

### 步骤 4：清理 backups/ 冗余

多份主题备份（2026-08-29、2026-08-30）占空间，Git 已能承担版本管理。

## 5. 风险与注意

- **WordPress 数据模型迁文档型数据库 = 重写 WordPress**，是典型的错误迁移。
- WP 插件生态深度依赖 MySQL，换库后插件大面积失效风险极高。
- 240 个文件里 public/（WP 核心）+ backups/ 占绝大部分，真实自研代码很少。
