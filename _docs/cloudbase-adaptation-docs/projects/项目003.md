# 项目003 · CloudBase 适配方案

> 适配等级：**B · 后端可迁** ｜ 预估工作量：**3–4 天** ｜ 代码改动：**中等偏大**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | PostgreSQL（27 处）+ Go（14 处）+ Electron（8 处）+ REST（7 处） |
| 源文件规模 | 191 个源文件 |
| 当前数据层 | PostgreSQL 为主（email-aggregator/package.json 等 27 处） |
| 认证方式 | 未检出独立认证（platforms/desktop 有 1 处信号） |
| 文件/存储 | 未见文件存储 |
| 后端形态 | Go 服务（email-aggregator-go）+ Node（email-aggregator）+ EdgeOne 云函数部署 |
| 已接入云服务 | **无** CloudBase；deploy/edgeone-app/cloud-functions/api/[[default]].js 走 EdgeOne |

邮箱聚合平台，PG 为数据存储，Go + Node 双后端，部署在 EdgeOne。
`deploy/edgeone-app/cloud-functions/api/[[default]].js` 是 EdgeOne 的 catch-all 云函数 ——
说明后端已经是"单入口函数"形态，**这种形态迁 CloudBase 云函数成本很低**。

Go 部分（email-aggregator-go）是独立服务，需评估是否一并上云。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| PostgreSQL（27 处） | CloudBase PostgreSQL | 同构迁移，schema 不变 |
| EdgeOne catch-all 云函数 | CloudBase 云函数 | 单入口形态，迁移成本低 |
| Go 服务 | 云托管 CloudRun | Go 编译产物适合容器化托管 |
| Node 服务（email-aggregator） | 云函数 或 云托管 | 按是否长驻决定 |
| 邮箱 IMAP 轮询 | 云函数定时触发器 | **天然契合**：定时拉取邮件正是云函数定时触发的典型场景 |

## 3. 接入点（需要改动的具体位置）

1. `email-aggregator/package.json —— PG 依赖声明`
2. `email-aggregator-go/cmd/*.go —— Go 服务入口`
3. `deploy/edgeone-app/cloud-functions/api/[[default]].js —— EdgeOne catch-all 函数`
4. `email-aggregator-web/src/api/client.ts —— Web 端接口`
5. `platforms/desktop/ —— Electron 桌面端`

## 4. 改造步骤

### 步骤 1：数据库先迁

PG → CloudBase PG，同构迁移风险最低，先做这一步建立信心。

### 步骤 2：云函数迁移（单入口，成本低）

[[default]].js 这种 catch-all 形态迁 CloudBase 云函数几乎是一比一映射。

### 步骤 3：邮件轮询改定时触发

邮箱聚合必然有定时拉取逻辑，用云函数定时触发器替代常驻进程，
**能省掉一台常驻服务器**。

### 步骤 4：Go 服务上云托管

Go 编译为静态二进制，容器化后放云托管。

## 5. 风险与注意

- Go + Node 双后端并存，需先明确各自职责边界，避免重复迁移。
- 邮箱 IMAP 连接是长连接场景，云函数（短生命周期）需重新设计连接复用策略。
- PG 27 处信号多为 package.json/package-lock.json，实际代码依赖面需二次确认。
- 邮件数据涉及隐私，上云需评估合规与加密存储要求。
