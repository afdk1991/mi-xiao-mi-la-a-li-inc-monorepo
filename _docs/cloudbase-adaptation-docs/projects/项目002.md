# 项目002 · CloudBase 适配方案

> 适配等级：**D · 桌面应用（仅建议云端辅助能力）** ｜ 预估工作量：**1 天（可选）** ｜ 代码改动：**小（增量）**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | Electron（24 处）+ Redis（10 处）+ REST（1 处，capabilityFeed.ts） |
| 源文件规模 | 114 个源文件 |
| 当前数据层 | Redis 10 处（electron/main.ts、dllrepair.ts）；localStorage 3 处 |
| 认证方式 | 认证 2 处（dllrepair.ts） |
| 文件/存储 | 本地文件（Electron 桌面应用） |
| 后端形态 | **无服务端** —— 纯桌面应用（gale-engine 疾风引擎） |
| 已接入云服务 | **无** CloudBase 接入 |

疾风引擎是 Electron 桌面应用，**本质上是本地软件，没有服务端** ——
这是它与 CloudBase 关系的根本约束：CloudBase 是后端 BaaS，而本地应用不需要后端。

强行上云没有意义。真正有价值的云端能力只有三个：
**配置同步**（用户设置跨设备）、**遥测/崩溃上报**、**能力清单下发**（capabilityFeed.ts 已经在做类似的事）。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| electron/services/capabilityFeed.ts | 云函数 / 云数据库下发 | **已在做**能力清单拉取，接 CloudBase 最自然 |
| 用户配置（localStorage 3 处） | 云数据库（需登录） | 跨设备同步配置 |
| 崩溃/遥测上报 | 云函数 + 云数据库 | 本地应用的典型云端需求 |
| Redis（10 处） | **本地缓存，不迁** | 桌面端 Redis 是本地缓存，与云无关 |

## 3. 接入点（需要改动的具体位置）

1. `electron/services/capabilityFeed.ts —— 唯一的 REST 调用点，云端能力下发入口`
2. `electron/main.ts —— Redis 与主进程逻辑`
3. `electron/services/dllrepair.ts —— 认证信号点`
4. `landing/index.html —— 落地页，可迁静态托管`

## 4. 改造步骤

### 步骤 1：明确：这不是迁移项目

桌面应用上云的正确姿势是"加云端能力"，不是"迁到云上"。
先接受这一点，能省掉大量无谓改造。

### 步骤 2：能力清单下发接 CloudBase（最自然的一步）

capabilityFeed.ts 已经在拉取远端能力清单，
把数据源换成 CloudBase 云数据库/云函数即可，改动最小。

### 步骤 3：落地页迁静态托管

landing/index.html 可迁 CloudBase 静态托管，省一台服务器。

### 步骤 4：可选：配置同步与遥测

若要跨设备同步配置或收集崩溃上报，再引入认证 + 云数据库。
**这是加分项，不是必须项。**

## 5. 风险与注意

- **桌面应用不需要后端** —— 不要把 CloudBase 当成必须项，会导致过度设计。
- Redis 10 处是本地缓存用途，与云端 Redis 无关，不要误迁。
- landing/index.html 若已在 EdgeOne 部署，迁静态托管属于重复建设，需先确认收益。
