# 项目008采集 · CloudBase 适配方案

> 适配等级：**B+ · 已接入 CloudBase，需深化** ｜ 预估工作量：**2–3 天** ｜ 代码改动：**中等（增量改造）**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | Python 采集器 + CloudBase 云函数（已接入）+ Web 前端 |
| 源文件规模 | 228 个源文件（REST 调用 126 处） |
| 当前数据层 | REST 126 处；Redis 6 处（lazada.py、temu.py 采集源） |
| 认证方式 | 无独立认证 |
| 文件/存储 | COS 相关脚本（_put_cos.py、_put_cos2.py）；未见云存储 SDK |
| 后端形态 | **已有 CloudBase 云函数**：cloudbase/scf-priceprobe/；另有 cloudbase-fn/、cloudbase-loader/ |
| 已接入云服务 | **已深度接入** —— build_cloudbase_fn.py、build_scf.py、cloudbase/scf-priceprobe.zip 均在 |

这是 16 个项目里**唯一已经跑在 CloudBase 上的**：`cloudbase/scf-priceprobe/` 是完整的
云函数工程（pipeline / cleaning / scoring / analysis / ai / models），还有 build_cloudbase_fn.py 做构建。

所以这里不是"要不要迁"，而是**怎么把已上云的部分用得更彻底**：
目前只用了云函数（算力），**没用云数据库、云存储、定时触发器** —— 数据大概率还在 COS 或本地文件。

另注：`_put_cos.py` / `_put_cos2.py` 说明你在往 COS 写，CloudBase 云存储可替代这部分。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| cloudbase/scf-priceprobe（已上云） | 保留，补定时触发器 | 采集任务应配定时触发器，而不是手动触发 |
| COS 存储（_put_cos.py） | CloudBase 云存储 | 与云函数同环境，权限统一；或保留 COS 若已有大量存量数据 |
| Redis（lazada/temu 采集源） | 云数据库 或 云函数内存缓存 | 云函数无长驻 Redis，短周期缓存可用内存；跨调用缓存需上云 Redis |
| 采集结果落盘 | 云数据库集合（MySQL/PG） | **当前最大缺口**：结构化采集结果应入库可查询，而非只写文件 |
| 构建脚本 build_cloudbase_fn.py | 保留，接 CI | 已有构建脚本，接 GitHub Actions 即可自动化 |

## 3. 接入点（需要改动的具体位置）

1. `cloudbase/scf-priceprobe/index.py —— 云函数入口，补定时触发配置`
2. `cloudbase/scf-priceprobe/price_collector/pipeline.py —— 采集主流程，落库改造点`
3. `cloudbase/scf-priceprobe/price_collector/models.py —— 数据模型，对接云数据库 schema`
4. `_put_cos.py / _put_cos2.py —— COS 写入，评估是否切云存储`
5. `deploy/cloud-functions/api、price_collector —— 部署副本，需与 cloudbase/ 同步`
6. `build_cloudbase_fn.py —— 构建脚本，保留`

## 4. 改造步骤

### 步骤 1：采集结果入库（最大缺口）

models.py 已有数据模型，直接映射成 CloudBase MySQL/PG 表。
**采集数据只有入库才有价值** —— 现在写文件等于采集完就丢。

### 步骤 2：配定时触发器

采集是周期性任务，应在云函数配 cron 触发器自动跑，而不是手动执行。

### 步骤 3：统一 cloudbase/ 与 deploy/ 两套副本

两个目录都有 price_collector，**存在版本漂移风险**。确定单一源后删除另一份，或明确主从关系。

### 步骤 4：COS 与云存储二选一

若 COS 已有大量存量数据且业务依赖，保留 COS；若数据量不大，统一到云存储简化权限。
**不要两套并存** —— 权限和路径管理会失控。

### 步骤 5：接 CI 自动部署

build_cloudbase_fn.py 已具备构建能力，接 GitHub Actions（项目已有 .github/）即可。

## 5. 风险与注意

- **cloudbase/ 与 deploy/ 两套 price_collector 副本**是最大隐患，改一处漏一处。
- 云函数无长驻 Redis —— 若采集依赖 Redis 做去重/队列，需改用云数据库或消息队列，否则功能会失效。
- 采集类任务有超时限制（云函数默认较短），长耗时采集需拆分或改云托管。
- 采集频率过高可能触发目标站点封禁，定时触发前先评估频率。
