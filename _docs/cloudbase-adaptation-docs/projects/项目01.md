# 项目01 · CloudBase 适配方案

> 适配等级：**C · 重资产（不建议整体迁移）** ｜ 预估工作量：**不建议全量；分模块 5 天+** ｜ 代码改动：**大（若全量）**

## 1. 现状诊断

| 维度 | 现状 |
|---|---|
| 技术栈 | WordPress/PHP（39 处）+ 微服务集群（MySQL 18 / Redis 15 / Express 16 / Nest 2）+ uni-app（12）+ Electron（17）+ Go（20）+ FastAPI（19） |
| 源文件规模 | 512 个源文件（16 个项目中最大） |
| 当前数据层 | MySQL 18 处、SQLite 19 处、PostgreSQL 10 处、MongoDB 3 处、Redis 15 处、Prisma 7 处 —— **六种数据存储并存** |
| 认证方式 | 认证 23 处（ai-saas-backend、mixmlaal-auth-service） |
| 文件/存储 | 文件上传 13 处 |
| 后端形态 | Mi-Xiao-Mi-La-A-Li-Inc/02-后端微服务集群/ 下多个服务：mixmlaal-auth-service、analytics-service、sms-service、kafka-consumer-service 等 |
| 已接入云服务 | **无** CloudBase 接入 |

这是 16 个项目里体量最大、技术栈最杂的一个 —— 512 个源文件横跨 PHP、Node、Go、Python、
uni-app、Electron，数据层同时存在 **MySQL / SQLite / PG / MongoDB / Redis / Prisma** 六种。

**核心判断：这个项目不该整体迁移到 CloudBase。** 它已经是自建微服务架构，
强行迁到 CloudBase 等于推翻重来，收益远小于成本。

真正适合 CloudBase 的是其中**特定的轻量级模块**（如卫星产品、uni-app 小程序端），
而不是整个微服务集群。

## 2. CloudBase 能力映射

| 现有能力 | CloudBase 对应 | 迁移方式 |
|---|---|---|
| 微服务集群（auth/analytics/sms/kafka-consumer） | **保持自建，不迁** | 已是成熟微服务架构，迁 CloudBase 是重写 |
| uni-app 小程序端（12 处） | CloudBase 小程序 SDK | 可独立接入，不影响后端 |
| WordPress 卫星产品 | 保持自建 或 静态化托管 | PHP+MySQL 迁 CloudBase 需重写数据层，不划算 |
| Kafka 消费者 | **无法迁云函数** | 长驻消费进程，云函数不适用；需云托管且要保留 Kafka |

## 3. 接入点（需要改动的具体位置）

1. `Mi-Xiao-Mi-La-A-Li-Inc/03-全平台应用端/uniapp-mini/ —— 唯一低风险接入点`
2. `Mi-Xiao-Mi-La-A-Li-Inc/03-全平台应用端/mixmlaal-miniapp/mixmlaal-utils/auth.js —— 小程序认证`
3. `Mi-Xiao-Mi-La-A-Li-Inc/03-全平台应用端/mixmlaal-miniapp/mixmlaal-platforms/adapter.js —— 平台适配层`
4. `Mi-Xiao-Mi-La-A-Li-Inc/02-后端微服务集群/ —— **建议保持不动**`
5. `daijia-dist/、daijia-dist_old_*/ —— 构建产物，改造排除`

## 4. 改造步骤

### 步骤 1：先做减法：清理构建产物与旧快照

daijia-dist_old_20261002_141312/、20-归档-旧快照/ 等目录应清理或移出。
512 个源文件里**很大一部分是历史快照和构建产物**，不是活跃代码。

### 步骤 2：只迁 uni-app 小程序端（唯一推荐动作）

小程序端接 CloudBase SDK 不影响现有后端，风险可控、收益明确。
这是本项目**唯一值得做的 CloudBase 动作**。

### 步骤 3：数据层六种并存 —— 先收敛再谈云

MySQL/PG/SQLite/MongoDB/Redis/Prisma 同时存在是**架构债**，
不是 CloudBase 能解决的问题。上云前应先收敛，否则只是把混乱搬到云端。

### 步骤 4：微服务集群保持自建

Kafka 消费者、SMS 服务等长驻组件不适合云函数。
若确实要上云，落点是**云托管**，且 Kafka 仍需自建或买托管服务。

## 5. 风险与注意

- **整体迁移是错误方向** —— 512 文件 / 六种数据库 / 多语言微服务，迁移成本极高且收益不明确。
- Kafka 消费者是长驻进程，云函数完全不适用，不要误判。
- 扫描命中的 512 个文件含大量构建产物与归档快照，据此评估工作量会严重失真。
- Prisma + MySQL + MongoDB 并存说明 ORM 层未统一，任何数据层改造都会牵一发动全身。
